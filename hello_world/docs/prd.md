## 0. 先更正一个术语

需求原文写的是「**TTS 转写工具**」。这两个词是反的：

| 缩写 | 全称 | 方向 |
|---|---|---|
| **STT / ASR** | Speech-to-Text | 语音 → **文字** ← **本项目要做的** |
| TTS | Text-to-Speech | 文字 → 语音 |

你列的四条需求（收音、转写、总结、按键）**全部**是 STT。我按 STT 来写。

> 你本机装了 CosyVoice（TTS 引擎），所以我在澄清阶段专门问过「最后要不要读出来」——你确认**不要**。所以 TTS 不在本 PRD 范围内。如果以后想加，见 §12 开放问题。

## 1. 问题与目标

### 1.1 要解决什么

想要一个**可以随手说话的速记设备**：按一下开始讲，电脑上实时出文字，并且持续把讲过的东西滚动总结成要点。不用掏出手机、不用打开 App、不用登录某个云笔记。

### 1.2 目标（可判定）

| # | 目标 | 判定方式 |
|---|---|---|
| G1 | 说话时，文字**边说边出**，不用等说完 | 讲一句话，句尾说完前屏幕上已有前半句 |
| G2 | 讲的内容被**持续重新总结** | 讲 2 分钟，终端出现至少 5 次刷新过的总结块 |
| G3 | 全链路**不依赖任何云服务** | 拔掉网线仍能工作（WiFi 阶段除外：此时只需局域网） |
| G4 | 整条链路**可换成云 ASR**，且改动局限在一个文件 | 换 provider 只需新增一个模块，不改 `session.py` |

### 1.3 不做什么（Non-goals）

明确排除，避免范围蔓延：

- ❌ **板端语音识别** —— 板子只采音、打包、传，`espressif/esp-sr` 那套不引入
- ❌ **板端存储/回放** —— 8MB Flash 和 2MB PSRAM 不做音频缓存（理由见 §11-R12）
- ❌ **TTS 语音播报** —— 已确认不做
- ❌ **多麦克风阵列 / 波束成形 / 降噪** —— 单麦克风，噪声处理交给 ASR 模型
- ❌ **唤醒词（"小爱同学"那种）** —— 用物理按键触发，不做 always-on 监听
- ❌ **说话人分离（谁在说）** —— 不在 v1
- ❌ **云端 ASR 的实际接入** —— 只留接口，见 §12 与 `cloud-asr.md`
- ❌ **移动端 / Web UI** —— 终端优先

## 2. 用户与场景

### 2.1 主流程

```
1. 用户在 PC 上启动     python -m voice_notes
2. 终端显示             ● 就绪，等待开始
3. 用户触发开始          阶段2-5: 敲 start    阶段6: 按板上的键
4. 终端显示             ● 录音中 00:12
                        ── 实时转写 ──────────────
                        今天下午我们讨论了三件事
                        ── 总结（每 20s 刷新）────
                        · 讨论了三个议题
5. 用户讲完              再按一次键 / 敲 stop / 静音 5 秒
6. 终端显示最终结果      全文转写 + 最终总结
7. 落盘                  sessions/2026-09-19_143022.json + .txt
```

### 2.2 状态机

**固件侧**（只管音频，不管语义）：

```
         START (串口帧 / 按键)
  IDLE ────────────────────────> RECORDING
    ^                                │
    └──────────── STOP ──────────────┘
```

**PC 侧**（真正的大脑）：

```
  IDLE ──start──> RECORDING ──stop──> FINALIZING ──> IDLE
                     │                    │
                     │                    └ 等 ASR is_final
                     │                      输出尾巴 → 落盘
                     ├─ 每 20s 触发后台总结线程
                     └─ VAD 静音 5s ──> 自己发 STOP
```

> ⚠️ **`FINALIZING` 不是可有可无的。** 停止时必须给 ASR 喂一个 `is_final=True`
> 的空/尾块，否则**最后几个字永远出不来**（FunASR 的流式缓存会把它留在
> decoder 里）。这是最容易漏掉、且表现为"偶尔少半句话"的坑。

## 3. 功能需求

### FR-1 音频采集

| 项 | 值 | 依据 |
|---|---|---|
| 麦克风 | ICS-43434 | 你指定 |
| 采样率 | **16 000 Hz** | 见 §6.2 |
| 位深（采集） | 24 bit（芯片原生） | 数据手册 |
| 位深（传输） | **16 bit** | ASR 标准输入，省一半带宽 |
| 声道 | 单声道（取左声道） | LR 脚接地 |
| 数据手册约束 | 每 WS 帧**正好 64 个 SCK** | DS-000069 §"I²S DATA INTERFACE" |

**验收**：录 10 秒人声，PC 上播放**能听清**；静音段样本幅度接近 0。

### FR-2 传输（两条都要，共用一套帧格式）

| 路径 | 状态 | 说明 |
|---|---|---|
| USB 串口 | 阶段 2 | 921600 8N1，复用现有 CP2102N |
| WiFi TCP | 阶段 5 | ESP32 做 client，推给 PC |

**验收（串口）**：连续录 60 秒，丢帧数 = 0（用帧序号 `seq` 统计）。
**验收（WiFi）**：同样 60 秒，转写结果与串口路径**一致**。

### FR-3 流式转写

- 引擎：**FunASR `paraformer-zh-streaming`**（本地 GPU）
- 分块：`chunk_size = [0, 10, 5]` → **600 ms 一块 + 300 ms lookahead**
- 已出的字**可以被后续块修正**（流式模型的正常行为，UI 要能原地刷新）
- **停止时必须 flush**（见 §2.2 警告）

**验收**：讲 10 句普通话，转写结果**肉眼可接受**（不要求零错误）。

### FR-4 滚动总结

- 引擎：**本地 ollama**，模型 `qwen2.5:7b`
- 触发：录音中每 **20 秒**，把**至今全文**重新总结一次
- 停止时再出一次**最终定稿**
- `temperature = 0`，保证同一份输入结果稳定（否则每次刷新都在抖，很难看）

> ⚠️ **总结必须跑在后台线程。** 7B 模型总结一次约 2–3 秒；如果同步跑，
> 转写显示会卡住 2–3 秒 —— 这直接违反 G1。

**验收**：讲 2 分钟，总结块刷新 ≥ 5 次，且**转写行不受阻**。

### FR-5 会话控制

| 触发方式 | 阶段 |
|---|---|
| 终端敲 `start` / `stop` | 2–5 |
| 物理按键（按一下开始 / 再按结束） | 6 |
| 静音 5 秒自动结束 | 3 |

静音检测：对 16-bit PCM 算 RMS，低于阈值持续 5 秒即触发 STOP。
初始阈值 **−45 dBFS**（≈ RMS 184），**必须现场标定**（见 §11-R9）。

### FR-6 落盘

每次会话产出 `sessions/<时间戳>.json`：

```json
{
  "started_at": "2026-09-19T14:30:22+08:00",
  "duration_s": 137.4,
  "transcript": "……全文……",
  "summary": "……最终总结……",
  "summary_history": ["……第1次……", "……第2次……"],
  "audio": "sessions/2026-09-19_143022.wav",
  "stats": {"frames_received": 8571, "frames_lost": 0, "asr_provider": "funasr"}
}
```

**WAV 可选**：默认存（`config.toml` 里 `save_audio = true`）。存 WAV 的价值是
**调 ASR 参数时可以离线重放**，不用重新对着麦克风说话。

### FR-7 按键（阶段 6）

- 按一下开始，再按一下结束
- **必须做软件消抖**（20 ms）—— 机械按键抖动会产生多次边沿
- GPIO 待定，避开 strapping 脚（0 / 2 / 12 / 15）

### FR-8 配置

`config.toml` 集中管理，不在代码里硬编码：

```toml
[transport]
mode = "serial"          # serial | tcp
serial_port = "/dev/ttyUSB0"
serial_baud = 921600
tcp_listen = "0.0.0.0:9999"

[asr]
provider = "funasr"      # funasr | (未来) cloud_aliyun | cloud_xfyun
device = "cuda"
chunk_size = [0, 10, 5]

[summary]
provider = "ollama"
model = "qwen2.5:7b"
interval_s = 20
temperature = 0

[session]
save_audio = true
silence_threshold_dbfs = -45
silence_timeout_s = 5
```

## 4. 非功能需求

### NFR-1 延迟预算（拆开算，不含糊）

| 环节 | 耗时 | 说明 |
|---|---|---|
| 麦克风 group delay | 0.1 ms | 手册：`2/fS` |
| I²S DMA 缓冲 | 64 ms | 4 buffer × 256 帧 |
| 串口传输 | 6 ms | 527 B @ 92160 B/s |
| PC 解帧 | ~1 ms | |
| **ASR 分块 + lookahead** | **900 ms** | 600 ms 块 + 300 ms 前瞻 |
| 终端渲染 | ~1 ms | |
| **合计** | **≈ 0.97 s** | |

> **结论：延迟由 ASR 决定，不由链路决定。** 想把延迟压到 0.5 s 以下，只能改
> `chunk_size = [0, 8, 4]`（480 ms + 240 ms），代价是识别率略降。链路怎么优化
> 都省不出这 900 ms。

### NFR-2 不丢帧

- 帧带 `seq` 序号，PC 侧统计缺口
- 丢帧数**显示在终端状态栏**，不静默
- v1 **不做重传** —— 音频流重传的收益不值复杂度，丢一帧 = 32 ms 音频，ASR 能扛

### NFR-3 采样率精度

- I²S 时钟源用 **`I2S_CLK_SRC_APLL`**（已确认经典 ESP32 支持）
- 用默认 PLL 分频时 160 MHz ÷ 1.024 MHz 不是整数，会有小数分频误差；
  长时间录音会累积成可感知的音调偏移，进而影响识别率

### NFR-4 可测试性

每个阶段都要能**单独验收**（见 §10），不允许"全部写完再一起测"。

| 抽象 | 挡住的变更 | 你的原话 |

换任何一个实现，**不改下游一行代码**。这是 G4 的达成方式。

## 6. 硬件

### 6.1 数据手册硬约束（`docs/modules/ICS-43434.PDF`，DS-000069 Rev 1.2）

我读了原始数据手册，以下四条是**设计的地基**，任何一条搞错都会导致
「能收到数据但听不清」这种极难反推的故障：

| # | 约束 | 原文依据 |
|---|---|---|
| C1 | I²S **slave**（ESP32 做 master 供时钟） | Pin 描述：WS/SCK 均为 Input |
| C2 | **每 WS 帧必须正好 64 个 SCK** | "There must be 64 SCK cycles in each WS stereo frame" |
| C3 | **MSB 比半帧起点延迟 1 个 SCK** = 标准 Philips I²S | "the MSB of each word is delayed by one SCK cycle from the start of each half-frame" |
| C4 | SD 是**三态输出**，需 **100 kΩ 下拉** | "This pin tristates when not actively driving" |

### 6.2 采样率为什么是 16 kHz

数据手册 Table 5 给的采样率范围：

| 模式 | 范围 | 功耗 |
|---|---|---|
| Sleep | ≤ 3.125 kHz | 12 µA |
| **Low-Power** | **6.25 – 18.75 kHz** | 230 µA |
| **High-Performance** | **23 – 51.6 kHz** | 490 µA |

⚠️ **18.75 – 23 kHz 之间是空档。** 16 kHz 只存在于 Low-Power 模式。

那为什么不选 48 kHz 去拿高性能模式？因为**收益几乎为零**：

| | Low-Power @16 kHz | High-Performance |
|---|---|---|
| SNR | **64 dBA** | 65 dBA |
| EIN | 30 dBA SPL | 29 dBA SPL |
| AOP | 120 dB SPL | 120 dB SPL |

**只差 1 dB**，而数据手册自己的 Low-Power 表**就是在 16 kHz 下标定的**。
换来的是：数据量 1/3、不需要降采样（降采样本身会引入伪影）、功耗减半、
且 16 kHz 是所有 ASR 模型的原生输入。

→ **选 16 kHz / Low-Power 模式。**

### 6.3 接线

| ICS-43434 | 接到 ESP32 | 备注 |
|---|---|---|
| 1 · WS | **GPIO 25** | 帧同步，16 kHz |
| 2 · LR | **GND** | 拉低 → 数据出在左声道 |
| 3 · GND | GND | |
| 4 · SCK | **GPIO 26** | 位时钟，**1.024 MHz** |
| 5 · VDD | **3V3** | 1.65–3.63 V，就近并 **0.1 µF** 到 GND |
| 6 · SD | **GPIO 22** | 加 **100 kΩ 下拉**到 GND |

选这三个 GPIO 的理由：避开 GPIO 6–11（SPI Flash，**碰了必死机**）、
GPIO 0/2/12/15（strapping 脚，上电电平影响启动模式）、GPIO 1/3（UART0 console）。

> GPIO 25/26 在经典 ESP32 上兼作 DAC —— 本项目中不用 DAC，可以直接当 I²S 用。

详细接线图与零件清单见 **`hardware.md`**。

### 6.4 I²S 配置参数（含每个值的理由）

```c
i2s_chan_config_t chan_cfg = {
    .id = I2S_NUM_0,
    .role = I2S_ROLE_MASTER,        // C1: 麦克风是 slave，我们必须做 master
    .dma_desc_num = 4,              // 4 buffer
    .dma_frame_num = 256,           // ⚠️ 必须 ≤ 511，见下方推导
    .auto_clear = true,
};

i2s_std_config_t std_cfg = {
    .clk_cfg = {
        .sample_rate_hz = 16000,
        .clk_src = I2S_CLK_SRC_APLL,   // NFR-3: 精确时钟
        .mclk_multiple = I2S_MCLK_MULTIPLE_256,
    },
    .slot_cfg = I2S_STD_PHILIPS_SLOT_DEFAULT_CONFIG(
        I2S_DATA_BIT_WIDTH_32BIT,
        I2S_SLOT_MODE_STEREO),      // ⚠️ 必须 STEREO，见下方推导
    .gpio_cfg = {
        .mclk = I2S_GPIO_UNUSED,    // 麦克风不需要 MCLK
        .bclk = GPIO_NUM_26,
        .ws   = GPIO_NUM_25,
        .din  = GPIO_NUM_22,
        .dout = I2S_GPIO_UNUSED,
        .invert_flags = { false, false, false },
    },
};
```

#### ⚠️ 两个必须理解的数字

**(1) 为什么 `dma_frame_num` 必须 ≤ 511**

ESP-IDF 文档明确：`dma_buffer_size = dma_frame_num × slot_num × slot_bit_width / 8 ≤ 4092`

代入 stereo/32bit：`dma_frame_num × 2 × 4 ≤ 4092` → **`dma_frame_num ≤ 511`**。
取 256 → 缓冲 2048 B，每块 256 帧 = **16 ms**，4 块 = 64 ms 延迟。

**(2) 为什么必须 `I2S_SLOT_MODE_STEREO`（这是最容易踩的坑）**

ESP-IDF 文档：「One frame refers to all the sampled data in **one WS circle**」
即 **帧长 = slot_num × slot_bit_width**。于是：

| 配置 | 帧长 | 结果 |
|---|---|---|
| `MONO` + 32-bit | 32 SCK | ❌ **违反 C2**，麦克风数据错位 |
| **`STEREO` + 32-bit** | **64 SCK** | ✅ 正好满足 C2 |

**直觉上"单声道麦克风当然用 MONO"在这里是错的。** 麦克风要的是 64 SCK，
所以必须开成双声道、然后由我们**丢弃右声道那一半数据**。

**(3) 24 bit 数据落在哪里**

C3 说 MSB 延迟 1 个 SCK，所以 24 bit 数据在 32 bit 字的 **[31:8]**，
低 8 位是空的。转换到 16 bit PCM 就是右移 16 位：

```c
int32_t raw = buf[i * 2];        // 每帧 8 字节 = 2 个 u32；取左声道(偶数下标)
int16_t pcm = (int16_t)(raw >> 16);
```

**验收方法**：正常说话时 `pcm` 峰值应在 ±1000 ~ ±8000 之间；
若恒为 0 或满量程噪声，就是这里错了。

## 7. 传输协议

串口和 TCP **共用同一套帧格式**，所以 `SerialSource` 和 `TcpSource` 可以互换。

```
偏移   长度   字段      说明
─────────────────────────────────────────────────────────
0      2     magic     0xAA 0x55  —— 用于流中重新同步
2      1     type      0x01=音频  0x02=控制  0x03=状态
3      2     len       payload 长度，小端 u16
5      N     payload
5+N    2     crc16     CRC-16/CCITT-FALSE，覆盖 type+len+payload
─────────────────────────────────────────────────────────
```

### type 0x01 — 音频（ESP32 → PC）

```
0      4     seq       帧序号 u32，丢帧检测
4      4     ts_ms     板子上电后的毫秒数 u32
8      N     pcm       16 bit 小端 PCM，N 默认 512 字节（256 样本 = 16 ms）
```

### type 0x02 — 控制（PC → ESP32）

payload 是 ASCII 文本，无终止符：`START` / `STOP`

### type 0x03 — 状态（ESP32 → PC）

payload 是 ASCII 文本：`READY` / `RECORDING` / `ERROR <原因>`

### 带宽核对

| 项 | 计算 | 结果 |
|---|---|---|
| PCM 净速率 | 16000 × 2 B | 32 000 B/s |
| 每帧开销 | 7 B 头 / 512 B 净荷 | 1.4 % |
| 含帧头速率 | 32000 × 527/512 | **32 938 B/s** |
| 921600 8N1 净速率 | 921600 / 10 | 92 160 B/s |
| **占用率** | 32938 / 92160 | **35.7 %** ✓ |

> 115200 只有 11 520 B/s，**装不下** 33 KB/s —— 这就是波特率必须提上去的原因。

### 8.1 固件（新工程 `voice_notes/`，与 `hello_world/` 平级）

| 文件 | 职责 | 关键依赖 |

## 10. 里程碑与验收

每一阶段必须**独立验收通过**才进入下一阶段 —— 不允许"全写完再一起测"。

| 阶段 | 产出 | 验收标准 | 全局风险 |
|---|---|---|---|
| 1 | 固件能把音频存成 WAV | **能听清**；静音段≈0 | 🔴 **最高** |
| 2 | 实时流到 PC 存 WAV | 60 s 丢帧 = 0 | 🟡 |
| 3 | 终端实时出字 | 10 句识别可接受 | 🟡 |
| 4 | ollama 滚动总结 | 刷新 ≥5 次且不卡 | 🟢 |
| 5 | 换 `TcpSource` | 与串口结果一致 | 🟡 |
| 6 | 物理按键触发 | 按下开始/再按结束 | 🟢 |

**阶段 1 是全局风险点。** I²S 的 64-SCK-每帧（C2）、MSB 延迟 1 拍（C3）、
24bit 在 32bit 槽里的对齐 —— 这三个任何一个错，后面全白做，而且表现都是
"能收音但听不清"，极难反推。**必须先用示波器或数据合理性检查钉死。**

## 11. 风险登记册

| ID | 风险 | 触发条件 | 影响 | 缓解 / 验证 |
|---|---|---|---|---|
| **R1** | I²S 帧长错误 | 用了 `I2S_SLOT_MODE_MONO` | 麦克风数据错位，无声或全噪 | 必须 `STEREO`+32bit → 64 SCK。**验证：SCK ÷ WS = 64** |
| **R2** | 24→16 bit 位移错误 | 错写成 `>> 8` 或 `<< 8` | 极低音量或满量程噪声 | `raw >> 16`。**验证：说话时峰值 ±1000~±8000** |
| **R3** | DMA 缓冲超限 | `dma_frame_num > 511` | 初始化失败或数据错乱 | 用 256（`256×2×4 = 2048 ≤ 4092`） |
| **R4** | SD 悬空 | 没加 100 kΩ 下拉 | 右声道浮空，可能额外功耗/振荡 | 加下拉（C4）。单麦克风时影响小，但仍建议加 |
| **R5** | 采样率时钟误差 | 用默认 PLL 而非 APLL | 长时间录音音调漂移，识别率下降 | 用 `I2S_CLK_SRC_APLL`（已确认经典 ESP32 支持） |
| **R6** | FunASR 装不上 / 模型下不动 | modelscope 网络问题 | 阶段 3 卡住 | 先跑**非流式** `paraformer-zh` 验证环境，再切流式 |
| **R7** | ollama 没启动 | 默认就没起（已实测） | 阶段 4 卡住，且报错难懂 | PC 端启动时**主动探测 11434 并给明确提示**，不要抛裸异常 |
| **R8** | 串口被占用 | `idf.py monitor` 开着 | `multiple access on port` | 已知问题，先 `Ctrl+]` 退出监视器 |
| **R9** | 静音阈值不合适 | 环境噪声差异大 | 该停不停 / 不该停乱停 | −45 dBFS 只是起点，**必须现场标定**；用迟滞避免抖动 |
| **R10** | ICS-43434 已 EOL | 买不到 | 阶段 1 卡住 | 用 **ICS-43432**（引脚兼容，规格接近） |
| **R11** | WSL2 是 NAT 网络 | 阶段 5 WiFi 路径 | 板子连不上 PC 的 IP | 二选一：① 用 `netsh interface portproxy` 做端口转发；② 改用**串口为默认路径**，WiFi 仅在同一局域网的原生 Linux/双系统下用。**这是阶段 5 最可能翻车的地方** |
| **R12** | 掉线丢帧 | WiFi 抖动 / 串口溢出 | 转写缺字 | v1 不重传，靠 `seq` 统计并**显示**丢帧数。板端不做缓冲的理由：2 MB PSRAM 只能存 64 s，而 PC 近在咫尺，缓冲收益低、复杂度高 |
| **R13** | 推理时 GPU 被别的任务占了 | 你那 10 个 conda 环境里跑了别的 | 转写卡顿 | 用 `nvidia-smi` 确认显存；FunASR 220M 参数只占约 1 GB |
