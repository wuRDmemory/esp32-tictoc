## 变更记录

### v1.2（2026-10-04）— **引入 S3 目标板，判停前移板端**（重要）

**起因**：项目引入 **ESP32-S3-CAM** 作为目标板（PICO 继续用于调试）。
S3 支持 ESP-SR 的 **AFE / VAD / WakeNet9**，经典 ESP32 不支持 ——
这**推翻了 v1.1 时期若干决策的依据**（虽然部分结论仍然成立）。

| # | 改动 | 性质 |
|---|---|---|
| 1 | **新增 D13：判停从 PC 侧 RMS 前移到板端 AFE VAD** | 新决策 —— 用户要求参考 xiaozhi（"他的反应挺快的"） |
| 2 | §1.3「板端语音识别」**边界收窄** | **精确化** —— 不做 ASR、不理解内容；但**引入前端 VAD** |
| 3 | §1.3「唤醒词」标注**依据失效** | **待重审** —— 换 S3 后 WakeNet9 可用（`decisions.md` D12.2） |
| 4 | §1.3「板端存储」容量依据更新 | 硬件变了，理由要重算（2 MB → 8 MB PSRAM） |
| 5 | §11-R12 板端缓冲的理由更新 | 同上 |
| 6 | 状态行、硬件栏、§10 里程碑 | 事实更新 |

> ⚠️ **本版最重要的不是"加了个 VAD"，而是划清一条边界**：
> **"有没有人在说 / 说完了没" → 板端可以做；"说了什么" → 仍然不做**（D3 收窄）。
> 这条线守不住，项目就会滑向"在 MCU 上做 ASR"，而那是 D3 明确排除的方向。

### v1.1（2026-09-27）— **取消流式转写**（重要）

**用户判断**：流式转写没什么用；录音时只要显示"聆听中"，停止后整体转写即可。

**这是个净收益，不只是简化。** 它连带解锁了原先做不到的能力：

| | v1.0 流式 | **v1.1 非流式** |
|---|---|---|
| 模型 | `paraformer-zh-streaming` | `paraformer-zh`（离线） |
| 准确率 | 较低（只前瞻 300 ms） | **更高**（看完整句） |
| **标点** | ❌ 流式模型不输出标点 | ✅ `ct-punc` **恢复标点** |
| 复杂度 | 流式状态机 + `is_final` flush + 分块调参 | 一次调用喂整段 |

**标点是关键**：给 LLM 做总结时，无标点文本的效果差得多。

**连带修订**：D7.1（ASR 选型，原"真流式"理由已消失）、D8（滚动总结）、
NFR-1（延迟预算）、FR-3、FR-4、§2.2 状态机、§8 模块接口。

## 0. 先更正一个术语

需求原文写的是「**TTS 转写工具**」。这两个词是反的：

| 缩写 | 全称 | 方向 |
|---|---|---|
| **STT / ASR** | Speech-to-Text | 语音 → **文字** ← **本项目要做的** |
| TTS | Text-to-Speech | 文字 → 语音 |

你列的四条需求（收音、转写、总结、按键）**全部**是 STT。我按 STT 来写。

> 你本机装了 CosyVoice（TTS 引擎），所以我在澄清阶段专门问过「最后要不要读出来」——你确认**不要**。所以 TTS 不在本 PRD 范围内。如果以后想加，见 §12 开放问题。

## 1. 问题与目标

### 1.1 要解决什么

想要一个**可以随手说话的速记设备**：按一下开始讲，讲完电脑上就出**带标点的完整文字**，并总结成要点。不用掏出手机、不用打开 App、不用登录某个云笔记。

### 1.2 目标（可判定）

| # | 目标 | 判定方式 |
|---|---|---|
| G1 | 说完就能拿到**完整且带标点**的文字 | 停止后终端出现完整转写，且句子有标点 |
| G2 | 讲完的内容被**总结成要点** | 讲 2 分钟后，终端出现一段总结 |
| G3 | 全链路**不依赖任何云服务** | 拔掉网线仍能工作（WiFi 阶段除外：此时只需局域网） |
| G4 | 整条链路**可换成云 ASR**，且改动局限在一个文件 | 换 provider 只需新增一个模块，不改 `session.py` |

### 1.3 不做什么（Non-goals）

明确排除，避免范围蔓延：

- ❌ **板端语音识别（ASR）** —— 板子不跑识别模型、**不理解说了什么**，只采音、打包、传
  > ⚠️ **2026-10-04 边界收窄（D13）**：本条原先写作"`espressif/esp-sr` 那套不引入"，
  > **过于宽泛** —— ESP-SR 里既有**内容识别**（ASR / MultiNet 命令词）也有**前端信号处理**（AFE / VAD）。
  > 现在**要引入的是后者**：板端用 AFE 的 **VAD 判断"有没有人在说 / 说完了没"**（判停），
  > **但仍不识别说了什么**。一句话边界：**"有没有声音"可以做，"说了什么"不做。**
- ❌ **板端存储/回放** —— 不做**整段**音频缓存（理由见 §11-R12，容量依据已随双板更新）
  > ⚠️ 例外：Q8 的 **2 秒预录缓冲（64 KB）** 是**小环形缓冲**，不是整段缓存，不受此条限制
- ❌ **TTS 语音播报** —— 已确认不做
- ❌ **多麦克风阵列 / 波束成形** —— 单麦克风，物理上不成立（AFE 的 BSS / AEC 因此也用不上，它们需要多通道或参考信号）
  > ⚠️ **降噪（NS）不在此列** —— 单麦克风 NS 是可用的，是否启用待定
- ❌ **唤醒词（"小爱同学"那种）** —— 用物理按键触发，不做 always-on 监听
  > ⚠️ **2026-10-04：本条的能力依据已失效，待重审** —— 换 S3 后 WakeNet9 可用，
  > `wakeword-research.md` §2.1 的"技术死路"论证不再成立。见 `decisions.md` D12.2
- ❌ **说话人分离（谁在说）** —— 不在 v1
- ❌ **云端 ASR 的实际接入** —— 只留接口，见 §12 与 `cloud-asr.md`
- ❌ **移动端 / Web UI** —— 终端优先

## 2. 用户与场景

### 2.1 主流程

```
1. 用户在 PC 上启动     python -m voice_notes
2. 终端显示             ○ 就绪，等待开始
3. 用户触发开始          阶段2-5: 敲 start    阶段6: 按板上的键
4. 终端显示录音状态      ● 聆听中  00:42  ▂▄▆▅▃▂▁▁▂▃
                        （状态 + 计时 + 实时电平条，每秒刷新）

                        ⚠️ 录音期间**不做转写、不显示文字**（v1.1 变更）
                           电平条的唯一用途是让你确认麦克风真在工作 ——
                           这块模块灵敏度偏低，嘴远了会拾不到（见 hardware.md §7）

5. 用户讲完              再按一次键 / 敲 stop / 静音自动结束
                        ⚠️ 静音时长：现状 5 秒（PC 侧 RMS）
                           → D13 后由板端 VAD 判定，具体值待标定
6. 终端转写              ◐ 转写中  已录音 42 秒
                           VAD 切分 → 识别 → 标点
                        ✅ 转写完成（用了 8.2 秒）
7. 终端显示最终结果      全文转写（带标点） + 总结
8. 落盘                  sessions/2026-09-27_143022.json + .txt + .wav
```

### 2.2 状态机

**固件侧**（只管音频，不管语义）：

```
         START (串口帧 / 按键)
  IDLE ────────────────────────> RECORDING
    ^                                │
    └──────────── STOP ──────────────┘
                 ▲
                 │ 现状：STOP 只来自外部（串口帧 / 按键）
                 └ D13 后：★ S3 上也能由板端 VAD 自己发起
```

> ⚠️ **2026-10-04（D13）：固件第一次有了"语义判断"能力。**
> 上图 `STOP` 现在**只来自外部**；D13 之后，**S3 上的固件能自己判断"说完了"
> 并发起 STOP**。这是 §1.3「板端语音识别」那条非目标**第一次被实质性放宽** ——
> 放宽的是**前端信号处理（VAD）**，不是**内容识别（ASR）**。**这条线要守住。**

**PC 侧**（真正的大脑）：

```
  IDLE ──start──> RECORDING ──stop──> TRANSCRIBING ──> SUMMARIZING ──> IDLE
                     │                     │                │
                     │                     │                └ ollama 总结一次
                     │                     └ 整段喂 FunASR
                     │                        （VAD + 识别 + 标点）
                     │
                     ├─ 收到的 PCM 增量写入 sessions/*.wav
                     └─ VAD 静音 5s ──> 自己发 STOP
                        ⚠️ D13 后：这一条挪到板端（S3），PC 侧不再做判停
```

**v1.1 相比 v1.0 简化掉的**：

- ❌ `FINALIZING` 状态 —— 原设计要在停止时给流式 ASR 喂 `is_final=True` 尾块，
  否则最后几个字永远出不来。**整段转写没有这个问题**，因为模型看到的是完整音频。
- ❌ 后台总结线程 —— 原来要防止 7B 模型阻塞转写显示；现在转写本身就是一次性的，
  没有"显示被卡住"的问题。
- ❌ ASR 分块与 `cache` 状态管理。

**注意 `RECORDING` 期间 PCM 是增量落盘的**（边收边写 WAV），不是攒在内存里。
这样录音时长只受磁盘限制，不受内存限制；而且停止时 WAV 已经写好了，
直接把它交给 FunASR 即可。

## 3. 功能需求

### FR-1 音频采集

| 项 | 值 | 依据 |
|---|---|---|
| 麦克风 | ICS-43434 | 你指定 |
| 采样率 | **16 000 Hz** | 见 §6.2 |
| 位深（采集） | 24 bit（芯片原生） | 数据手册 |
| 位深（传输） | **16 bit** | ASR 标准输入，省一半带宽 |
| 声道 | 单声道（取左声道） | LR 脚接地 |
| 数据手册约束 | 每 WS 帧**正好 64 个 SCK** | DS-000069 §"I²S DATA INTERFACE" |

**验收**：录 10 秒人声，PC 上播放**能听清**；静音段样本幅度接近 0。

### FR-2 传输（两条都要，共用一套帧格式）

| 路径 | 状态 | 说明 |
|---|---|---|
| USB 串口 | 阶段 2 | 921600 8N1，复用现有 CP2102N |
| WiFi TCP | 阶段 5 | ESP32 做 client，推给 PC |

**验收（串口）**：连续录 60 秒，丢帧数 = 0（用帧序号 `seq` 统计）。
**验收（WiFi）**：同样 60 秒，转写结果与串口路径**一致**。

### FR-3 整体转写（v1.1：原为「流式转写」）

**触发**：STOP 之后，对**整段录音**做一次转写。

**引擎**：FunASR **离线全链路**（本地 GPU）

```python
from funasr import AutoModel

model = AutoModel(
    model      = "paraformer-zh",   # 识别主模型，220M，16kHz
    vad_model  = "fsmn-vad",        # 语音活动检测，长音频自动分段，约 4MB
    punc_model = "ct-punc",         # 标点恢复，约 1.1GB
    device     = "cuda",
)
res = model.generate(input="sessions/xxx.wav", batch_size_s=300)
text = res[0]["text"]               # 带标点的全文
```

**关键约束**：

| # | 约束 | 后果 |
|---|---|---|
| 1 | **挂了 `vad_model` 时 `batch_size` 必须为 1** | 否则 FunASR 直接报错 |
| 2 | `batch_size_s=300` 是长音频的批处理秒数 | 太长会 OOM，太短会慢 |
| 3 | 三个模型合计约 **2 GB**，首次运行自动下载到 `~/.cache/modelscope/` | **需要联网**，只在第一次 |
| 4 | 已知问题：长音频有约 10s/3min 的时间戳漂移 | **v1 不需要时间戳，不受影响** |

> ⚠️ **转写期间终端必须有进度反馈。** 5 分钟录音约需 10~30 秒，安静地卡住
> 十几秒会让人以为程序死了。至少要有「转写中…」加上已耗时。

**验收**：讲 10 句普通话，转写结果**带标点**且肉眼可接受（不要求零错误）。

### FR-4 总结（v1.1：原为「滚动总结」）

- 触发：**转写完成后自动总结一次**（不再滚动）
- 引擎：**本地 ollama**，模型 `qwen2.5:7b`
- `temperature = 0` —— 保证同一份输入结果稳定，便于复现和对比
- 输入是**带标点的全文**（这正是 v1.1 的价值：标点显著提升总结质量）

**验收**：讲 2 分钟，终端出现一段连贯的总结。

### FR-5 会话控制

| 触发方式 | 阶段 |
|---|---|
| 终端敲 `start` / `stop` | 2–5 |
| 物理按键（按一下开始 / 再按结束） | 6 |
| 静音自动结束 | 3 |

> ⚠️ **2026-10-04（D13）：静音检测的实现端要改 —— 从 PC 侧挪到板端。**

**静音检测**：对 16-bit PCM 算 RMS，低于阈值持续一段时间即触发 STOP。
初始阈值 **−45 dBFS**（≈ RMS 184），**必须现场标定**（见 §11-R9）。

| | 现在（PICO / 阶段 3） | **D13 之后（S3）** |
|---|---|---|
| **检测在哪端** | PC 侧（收到 PCM 后算 RMS） | **板端 AFE VAD** |
| **依赖** | PC 在线 + 音频已送达 → **判停质量与链路质量耦合** | 板端独立，不受串口延迟/丢帧影响 |
| **静音时长** | **5 秒** —— 用户说完要干等 5 秒 | ⚠️ **待实测标定** |
| **VAD 形态** | SPEECH / SILENCE 状态转换 | **不变**（同形态，只换实现端） |

> **为什么"5 秒"需要重新考虑**：它当初是**为安全起见**（宁可多等，也别提前切断）——
> 那时检测在 PC 侧，没有更快的信号可用。换成板端 VAD 后，"快速判停"才有技术基础。
> **具体值必须在 S3 上实测**（参考 xiaozhi 的 `VAD_MODE_3`，`wakeword-research.md` §1.3）。

### FR-6 落盘

每次会话产出 `sessions/<时间戳>.json`：

```json
{
  "started_at": "2026-09-19T14:30:22+08:00",
  "duration_s": 137.4,
  "transcript": "……全文……",
  "summary": "……最终总结……",
  "summary_history": ["……第1次……", "……第2次……"],
  "audio": "sessions/2026-09-19_143022.wav",
  "stats": {"frames_received": 8571, "frames_lost": 0, "asr_provider": "funasr"}
}
```

**WAV 可选**：默认存（`config.toml` 里 `save_audio = true`）。存 WAV 的价值是
**调 ASR 参数时可以离线重放**，不用重新对着麦克风说话。

### FR-7 按键（阶段 6）

- 按一下开始，再按一下结束
- **必须做软件消抖**（20 ms）—— 机械按键抖动会产生多次边沿
- GPIO 待定，避开 strapping 脚（0 / 2 / 12 / 15）

### FR-8 配置

`config.toml` 集中管理，不在代码里硬编码：

```toml
[transport]
mode = "serial"          # serial | tcp
serial_port = "/dev/ttyUSB0"
serial_baud = 921600
tcp_listen = "0.0.0.0:9999"

[asr]
provider = "funasr"      # funasr | (未来) cloud_aliyun | cloud_xfyun
device = "cuda"
model = "paraformer-zh"  # 识别主模型
vad_model = "fsmn-vad"   # 长音频分段
punc_model = "ct-punc"   # 标点恢复
batch_size_s = 300       # 长音频批处理秒数；太大 OOM、太小慢
# ⚠️ 挂了 vad_model 时 batch_size 必须为 1（FunASR 的硬性要求）

[summary]
provider = "ollama"
model = "qwen2.5:7b"
temperature = 0          # 固定 0，保证同一份输入结果稳定

[session]
save_audio = true
silence_threshold_dbfs = -45
silence_timeout_s = 5
```

## 4. 非功能需求

### NFR-1 延迟预算（v1.1 全部重写）

**录音期间**：**没有任何转写延迟要求。** 只显示状态 + 计时 + 电平条，
不渲染文字。原来那套 0.97 秒的端到端预算（DMA 64ms → 串口 6ms → ASR 900ms）
**整个作废了**。

**停止之后**：

| 环节 | 耗时 | 说明 |
|---|---|---|
| 转写（VAD + 识别 + 标点） | **录音时长的 1/20 ~ 1/50** | paraformer 非自回归，GPU 上很快 |
| 总结（ollama qwen2.5:7b） | 2 ~ 5 s | |
| **合计（5 分钟录音）** | **约 10 ~ 30 s** | |

> **连带的一个好处：链路延迟完全不重要了。**
> 原来音频必须**实时**送到 PC（晚到就掉字）。现在 PC 只是边收边写 WAV，
> 早到晚到都无所谓 —— 只要**不丢**就行。
> → 阶段 2 的传输设计可以从"保证低延迟"改为"保证不丢帧"，两者取舍不同，
> 后者容易得多。

### NFR-1.1 转写期间必须有进度反馈（v1.1 新增）

`RECORDING` → `TRANSCRIBING` 之后终端会静默 10~30 秒。**必须显示进度**，
否则用户会以为程序卡死并强杀，而那时转写其实正在进行。

最低要求：显示当前阶段（VAD 切分 / 识别 / 标点）与已耗时。

### NFR-1.2 判停延迟（2026-10-04 新增，D13）

**这是用户唯一明确抱怨过的延迟** —— 原话是参考 xiaozhi 时说的「**他的反应挺快的**」。

| | 现状（PC 侧 RMS） | **D13 之后（板端 VAD）** |
|---|---|---|
| 判停延迟 | **静音持续 5 秒** = 说完干等 5 秒 | 待标定，目标**亚秒级** |
| 依赖 | PC 在线 + 音频已送达 | 板端独立 |

> ⚠️ **这一项不在 NFR-1 的"停止之后"预算里，别混淆**：
> NFR-1 算的是"**按下停止 → 出结果**"；判停延迟是"**说完话 → 系统知道你说完了**"，
> 发生在更早，而且**是纯等待**。
>
> **5 秒纯等待比 10~30 秒的转写更难受** —— 因为转写至少能看到进度（NFR-1.1），
> 而干等 5 秒时终端还写着"● 聆听中"，**用户根本不知道它在等什么**。

### NFR-2 不丢帧

- 帧带 `seq` 序号，PC 侧统计缺口
- 丢帧数**显示在终端状态栏**，不静默
- v1 **不做重传** —— 音频流重传的收益不值复杂度，丢一帧 = 32 ms 音频，ASR 能扛

### NFR-3 采样率精度

- **PICO（经典 ESP32）**：I²S 时钟源用 **`I2S_CLK_SRC_APLL`** —— 用默认 PLL 分频时
  160 MHz ÷ 1.024 MHz 不是整数，会有小数分频误差；长时间录音会累积成可感知的
  音调偏移，进而影响识别率
- ⚠️ **S3 没有 APLL**（`soc/esp32s3/clk_tree_defs.h` 的 `SOC_I2S_CLKS` 只有
  PLL_F240M / PLL_F160M / XTAL / EXTERNAL），只能用 **`I2S_CLK_SRC_DEFAULT`**（= PLL_F160M），
  同样是小数分频（156.25 分频）。**实测可用，但长时间累积误差未量化**
- 两块板的时钟源由 `board.h` 的 **`BOARD_I2S_CLK_SRC`** 选择，`i2s_mic.c` 不写死

### NFR-4 可测试性

每个阶段都要能**单独验收**（见 §10），不允许"全部写完再一起测"。

## 6. 硬件

### 6.1 数据手册硬约束（`docs/modules/ICS-43434.PDF`，DS-000069 Rev 1.2）

我读了原始数据手册，以下四条是**设计的地基**，任何一条搞错都会导致
「能收到数据但听不清」这种极难反推的故障：

| # | 约束 | 原文依据 |
|---|---|---|
| C1 | I²S **slave**（ESP32 做 master 供时钟） | Pin 描述：WS/SCK 均为 Input |
| C2 | **每 WS 帧必须正好 64 个 SCK** | "There must be 64 SCK cycles in each WS stereo frame" |
| C3 | **MSB 比半帧起点延迟 1 个 SCK** = 标准 Philips I²S | "the MSB of each word is delayed by one SCK cycle from the start of each half-frame" |
| C4 | SD 是**三态输出**，需 **100 kΩ 下拉** | "This pin tristates when not actively driving" |

### 6.2 采样率为什么是 16 kHz

数据手册 Table 5 给的采样率范围：

| 模式 | 范围 | 功耗 |
|---|---|---|
| Sleep | ≤ 3.125 kHz | 12 µA |
| **Low-Power** | **6.25 – 18.75 kHz** | 230 µA |
| **High-Performance** | **23 – 51.6 kHz** | 490 µA |

⚠️ **18.75 – 23 kHz 之间是空档。** 16 kHz 只存在于 Low-Power 模式。

那为什么不选 48 kHz 去拿高性能模式？因为**收益几乎为零**：

| | Low-Power @16 kHz | High-Performance |
|---|---|---|
| SNR | **64 dBA** | 65 dBA |
| EIN | 30 dBA SPL | 29 dBA SPL |
| AOP | 120 dB SPL | 120 dB SPL |

**只差 1 dB**，而数据手册自己的 Low-Power 表**就是在 16 kHz 下标定的**。
换来的是：数据量 1/3、不需要降采样（降采样本身会引入伪影）、功耗减半、
且 16 kHz 是所有 ASR 模型的原生输入。

→ **选 16 kHz / Low-Power 模式。**

### 6.3 接线

> ⚠️ **2026-10-04：本节及 §6.4 是 PICO 的参数。引脚与时钟源的唯一出处已改为
> `voice_notes/main/board.h`** —— 两块板**没有一个参数相同**，按板编译期选择，
> 不要照抄本节的数字去改代码。完整差异见 `s3-bringup.md` 与项目 `CLAUDE.md`：
>
> | | PICO-V3-02 | S3-CAM |
> |---|---|---|
> | BCLK / WS / DIN | 26 / 25 / 22 | **14 / 21 / 47** |
> | 时钟源 | `I2S_CLK_SRC_APLL` | `I2S_CLK_SRC_DEFAULT`（**S3 无 APLL**） |
>
> ⚠️ **GPIO22/25 在 S3 上物理不存在**（S3 只有 0–21、26–48），反过来给 S3 选的引脚
> 在经典 ESP32 上会撞 SPI Flash —— **这就是必须编译期选板、而不是共用一套引脚的原因。**

| ICS-43434 | 接到 ESP32 | 备注 |
|---|---|---|
| 1 · WS | **GPIO 25** | 帧同步，16 kHz |
| 2 · LR | **GND** | 拉低 → 数据出在左声道 |
| 3 · GND | GND | |
| 4 · SCK | **GPIO 26** | 位时钟，**1.024 MHz** |
| 5 · VDD | **3V3** | 1.65–3.63 V，就近并 **0.1 µF** 到 GND |
| 6 · SD | **GPIO 22** | 加 **100 kΩ 下拉**到 GND |

选这三个 GPIO 的理由：避开 GPIO 6–11（SPI Flash，**碰了必死机**）、
GPIO 0/2/12/15（strapping 脚，上电电平影响启动模式）、GPIO 1/3（UART0 console）。

> GPIO 25/26 在经典 ESP32 上兼作 DAC —— 本项目中不用 DAC，可以直接当 I²S 用。

详细接线图与零件清单见 **`hardware.md`**。

### 6.4 I²S 配置参数（含每个值的理由）

```c
i2s_chan_config_t chan_cfg = {
    .id = I2S_NUM_0,
    .role = I2S_ROLE_MASTER,        // C1: 麦克风是 slave，我们必须做 master
    .dma_desc_num = 4,              // 4 buffer
    .dma_frame_num = 256,           // ⚠️ 必须 ≤ 511，见下方推导
    .auto_clear = true,
};

i2s_std_config_t std_cfg = {
    .clk_cfg = {
        .sample_rate_hz = 16000,
        .clk_src = BOARD_I2S_CLK_SRC,  // NFR-3: 精确时钟
                                       // PICO=APLL / S3=DEFAULT(PLL_160M)，见 board.h
        .mclk_multiple = I2S_MCLK_MULTIPLE_256,
    },
    .slot_cfg = I2S_STD_PHILIPS_SLOT_DEFAULT_CONFIG(
        I2S_DATA_BIT_WIDTH_32BIT,
        I2S_SLOT_MODE_STEREO),      // ⚠️ 必须 STEREO，见下方推导
    .gpio_cfg = {
        .mclk = I2S_GPIO_UNUSED,    // 麦克风不需要 MCLK
        .bclk = GPIO_NUM_26,
        .ws   = GPIO_NUM_25,
        .din  = GPIO_NUM_22,
        .dout = I2S_GPIO_UNUSED,
        .invert_flags = { false, false, false },
    },
};
```

#### ⚠️ 两个必须理解的数字

**(1) 为什么 `dma_frame_num` 必须 ≤ 511**

ESP-IDF 文档明确：`dma_buffer_size = dma_frame_num × slot_num × slot_bit_width / 8 ≤ 4092`

代入 stereo/32bit：`dma_frame_num × 2 × 4 ≤ 4092` → **`dma_frame_num ≤ 511`**。
取 256 → 缓冲 2048 B，每块 256 帧 = **16 ms**，4 块 = 64 ms 延迟。

**(2) 为什么必须 `I2S_SLOT_MODE_STEREO`（这是最容易踩的坑）**

ESP-IDF 文档：「One frame refers to all the sampled data in **one WS circle**」
即 **帧长 = slot_num × slot_bit_width**。于是：

| 配置 | 帧长 | 结果 |
|---|---|---|
| `MONO` + 32-bit | 32 SCK | ❌ **违反 C2**，麦克风数据错位 |
| **`STEREO` + 32-bit** | **64 SCK** | ✅ 正好满足 C2 |

**直觉上"单声道麦克风当然用 MONO"在这里是错的。** 麦克风要的是 64 SCK，
所以必须开成双声道、然后由我们**丢弃右声道那一半数据**。

**(3) 24 bit 数据落在哪里**

C3 说 MSB 延迟 1 个 SCK，所以 24 bit 数据在 32 bit 字的 **[31:8]**，
低 8 位是空的。转换到 16 bit PCM 就是右移 16 位：

```c
int32_t raw = buf[i * 2];        // 每帧 8 字节 = 2 个 u32；取左声道(偶数下标)
int16_t pcm = (int16_t)(raw >> 16);
```

**验收方法**：正常说话时 `pcm` 峰值应在 ±1000 ~ ±8000 之间；
若恒为 0 或满量程噪声，就是这里错了。

## 7. 传输协议

串口和 TCP **共用同一套帧格式**，所以 `SerialSource` 和 `TcpSource` 可以互换。

```
偏移   长度   字段      说明
─────────────────────────────────────────────────────────
0      2     magic     0xAA 0x55  —— 用于流中重新同步
2      1     type      0x01=音频  0x02=控制  0x03=状态
3      2     len       payload 长度，小端 u16
5      N     payload
5+N    2     crc16     CRC-16/CCITT-FALSE，覆盖 type+len+payload
─────────────────────────────────────────────────────────
```

### type 0x01 — 音频（ESP32 → PC）

```
0      4     seq       帧序号 u32，丢帧检测
4      4     ts_ms     板子上电后的毫秒数 u32
8      N     pcm       16 bit 小端 PCM，N 默认 512 字节（256 样本 = 16 ms）
```

### type 0x02 — 控制（PC → ESP32）

payload 是 ASCII 文本，无终止符：`START` / `STOP`

### type 0x03 — 状态（ESP32 → PC）

payload 是 ASCII 文本：`READY` / `RECORDING` / `ERROR <原因>`

### 带宽核对

| 项 | 计算 | 结果 |
|---|---|---|
| PCM 净速率 | 16000 × 2 B | 32 000 B/s |
| 每帧开销 | 7 B 头 / 512 B 净荷 | 1.4 % |
| 含帧头速率 | 32000 × 527/512 | **32 938 B/s** |
| 921600 8N1 净速率 | 921600 / 10 | 92 160 B/s |
| **占用率** | 32938 / 92160 | **35.7 %** ✓ |

> 115200 只有 11 520 B/s，**装不下** 33 KB/s —— 这就是波特率必须提上去的原因。

#### `AsrProvider` 接口（v1.1 简化）

```python
class AsrProvider(ABC):
    @abstractmethod
    def transcribe(self, wav_path: str,
                   on_progress: Callable[[str], None] | None = None) -> str:
        """整段转写，返回带标点的全文。"""

    def warmup(self) -> None:
        """可选：预加载模型，避免首次调用卡十几秒。"""
```

**对比 v1.0 的流式接口**（`feed(pcm) -> partial` + `finalize() -> tail` + 分块常数
+ `cache` 状态管理）：整段接口**没有跨调用状态**，因此不存在"状态管理写错"
这一类 bug。云实现也更容易套 —— 云 API 多是上传整段音频返回整段文本。

> 这也说明为什么 §1.2 的 G4（可换云 ASR）在 v1.1 里**更容易达成**了。

| 6.2 | **决定接哪个 GPIO** | 避开 strapping 脚 0/2/12/15。推荐 **GPIO 27**（空闲、无复用冲突） |
| 6.3 | 接线 | 按键一端接 GPIO 27，另一端接 GND；用**内部上拉**（`GPIO_PULLUP_ENABLE`），省一个电阻 |

**验收**：按一下开始、再按一下结束，不误触发。

## 11. 风险登记册

| ID | 风险 | 触发条件 | 影响 | 缓解 / 验证 |
|---|---|---|---|---|
| **R1** | I²S 帧长错误 | 用了 `I2S_SLOT_MODE_MONO` | 麦克风数据错位，无声或全噪 | 必须 `STEREO`+32bit → 64 SCK。**验证：SCK ÷ WS = 64** |
| **R2** | 24→16 bit 位移错误 | 错写成 `>> 8` 或 `<< 8` | 极低音量或满量程噪声 | `raw >> 16`。**验证：说话时峰值 ±1000~±8000** |
| **R3** | DMA 缓冲超限 | `dma_frame_num > 511` | 初始化失败或数据错乱 | 用 256（`256×2×4 = 2048 ≤ 4092`） |
| **R4** | SD 悬空 | 没加 100 kΩ 下拉 | 右声道浮空，可能额外功耗/振荡 | 加下拉（C4）。单麦克风时影响小，但仍建议加 |
| **R5** | 采样率时钟误差 | 用默认 PLL 而非 APLL | 长时间录音音调漂移，识别率下降 | **PICO**：用 `I2S_CLK_SRC_APLL`（经典 ESP32 支持）<br>⚠️ **S3 无 APLL**，只能用 `I2S_CLK_SRC_DEFAULT`(PLL_160M)，同为小数分频（156.25）。**实测可用于短录音，但长时间累积漂移未量化** —— 见 NFR-3 |
| **R6** | FunASR 装不上 / 模型下不动 | modelscope 网络问题；**三个模型合计约 2 GB** | 阶段 3 卡住 | 先**只挂 `model` 不挂 `vad_model`/`punc_model`** 跑通环境，确认能出文本，再逐个加回 VAD 和标点 —— 这样能定位是哪个模型的问题 |
| **R7** | ollama 没启动 | 默认就没起（已实测） | 阶段 4 卡住，且报错难懂 | PC 端启动时**主动探测 11434 并给明确提示**，不要抛裸异常 |

| **R9** | 静音阈值不合适 | 环境噪声差异大 | 该停不停 / 不该停乱停 | −45 dBFS 只是起点，**必须现场标定**；用迟滞避免抖动 |

| **R12** | 掉线丢帧 | WiFi 抖动 / 串口溢出 | 转写缺字 | v1 不重传，靠 `seq` 统计并**显示**丢帧数。**板端不做整段缓冲**的理由：~~2 MB PSRAM 只能存 64 s~~，而 PC 近在咫尺，缓冲收益低、复杂度高<br>⚠️ **2026-10-04 更新**：S3 的 8 MB PSRAM 可存约 4 分钟，**"容量不够"这条理由已不成立**；但**结论暂不变** —— "PC 近在咫尺、收益低"与芯片无关。Q8 的 2 秒预录缓冲是唯一的板端缓冲，属例外 |

### Q8 详述：录音前 2 秒预录缓冲

**问题**：我们的触发方式是**按键**，而人往往是**先开口、再伸手按**。
于是**每句话的开头都被吃掉**。这不是 bug，是按键触发的固有缺陷。

**方案**（借鉴自 xiaozhi-esp32，见 `wakeword-research.md` §4）：
固件维护一个 2 秒环形缓冲，按下开始时**先把预录的 2 秒发出去**，再接实时数据。

| 项 | 值 |
|---|---|
| 内存 | 2 秒 × 16 kHz × 2 B = **64 KB**（2 MB PSRAM 中占 3%） |
| 实现 | 环形缓冲 + 录音开始时先冲一遍 |
| 收益 | **每句话的开头不再丢失** |

**建议在阶段 6（按键）时一并做** —— 正是"按键触发"让它变得必要。

> ⚠️ **2026-10-04 更正**：下面这条调研结论**基于经典 ESP32，换 S3 后已反转** ——
> AFE / VAD / WakeNet9 全部可用，而且 **VAD 正是 D13 要用的东西**。
>
> ~~顺带记录一个调研结论：xiaozhi 的唤醒词/AFE/VAD 架构在我们这块芯片上
> **不可用**（经典 ESP32 不支持 AFE，唤醒词只有两个官方型号且官方已停止更新）。~~
>
> 详见 `wakeword-research.md` 顶部注记。

### Q9 详述：静音时长是多少

**这是 D13 唯一需要现场决定的参数，而且是个真实的取舍**：

| 静音时长 | 后果 |
|---|---|
| 太短（如 0.5 s） | 用户**换气、思考、停顿**时被误判成"说完了"，**句子被切断** |
| 太长（如 5 s，即现状） | 失去前移的意义 —— 用户还是要干等 |

**建议做成可配置档位**（借鉴 xiaozhi 的 `VAD_MODE_0..3`，见 `wakeword-research.md` §5），
而不是写死一个值 —— 安静房间和嘈杂环境需要不同门限。**先实测出默认值**，再决定是否暴露成配置。

#### 📊 已实测的部分（2026-10-04）

当前值 **`vad_min_noise_ms = 1000`**（详见 `stage2-results.md` §8 与 D13 计划 §8.5）：

| 已确认 | 证据 |
|---|---|
| **判停延迟 = 1.00 秒** | 两次独立测量：`1.00s / 0.99s`，**精确等于设定值** —— 参数确实在起作用 |
| **换气不会被打断** | 实测有一段 **6.59 秒的连续 `speech`** —— 期间必然换气多次，VAD 一次都没误判 |
| **安静时不误报** | 38 秒零 `speech`（前提：`vad_mode` 必须用 3，见 D13 计划 §8.5） |
| 对比原来的 5 秒 | **快了 5 倍** |

#### ⬜ 仍未定的部分

**"说话中间思考停顿超过 1 秒"会被判停** —— 这是**数值上的必然而非猜测**
（门限就是 1000 ms），但对**语音笔记**场景是否可接受**还没专门验证**：

> 真实场景是"说一句 → 停下来想一下 → 接着说"，这个"想一下"经常超过 1 秒。
> 而 D13.3 决定固件**自己停**，所以一旦判停，**录音就结束了**，用户得重新开始。

**这条要等真实使用一段时间后再定** —— 现在有实测数据支撑，不必继续空测。

### Q10 详述：D13 的排期 —— ✅ **已解决（实际走了"先 D13"）**

| 路线 | 理由 |
|---|---|
| **先 D13，再阶段 3** ← **实际选的** | D13 改的是**固件状态机**（固件第一次能自己发 STOP），阶段 3 是 PC 侧转写。**先固件后软件**，避免阶段 3 的 PC 侧判停逻辑白写 |
| 先阶段 3，再回头 D13 | D13 必须在 S3 上实测标定 —— 当初的顾虑是"前置（S3 阶段 2 回归）还没做" |

**事后看，选"先 D13"是对的**，理由是**当时没预料到的**：

> **D13 改变了行为契约** —— 固件会自己发 STOP，于是"录满 N 秒"不再是必然。
> 阶段 2 的验收脚本因此误判过一次（`stage2_accept.py` 拿计划的 60 秒当基准，
> 而固件 41.5 秒就自停了，见 `stage2-results.md` §8.2）。
>
> **如果先做阶段 3**，那阶段 3 写出来的 PC 侧逻辑（等录满、再转写）会**整套假设"录音时长可控"**，
> 之后接 D13 时要一起返工。**先做 D13 反而避免了这个返工。**
