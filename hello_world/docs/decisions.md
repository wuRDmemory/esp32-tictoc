# 需求决策记录

本文档记录 **voice_notes 项目在做需求澄清时的每一个决策，以及支撑它的证据**。

**为什么单独记这个**：这些决策将来一定会被重新问到（"当初为什么选 16k 不选
48k？"）。没有依据的决策会被反复讨论；有依据的决策一句话就能结案。

记录格式：**决策 → 依据 → 备选方案为什么没选。**

---

## D1 · 术语：这是 STT 不是 TTS

| | |
|---|---|
| **决策** | 项目按 **STT / ASR**（语音→文字）实现，TTS（文字→语音）不在范围内 |
| **依据** | 用户四条需求（收音、流式转写、总结、按键）全部指向语音转文字。原始表述「TTS 转写工具」中 TTS 一词使用有误 —— TTS 是反方向 |
| **确认过程** | 已向用户当面确认「最后要不要读出来」，用户明确回答**不要，纯转写+总结** |

---

## D2 · 采样率：16 kHz / Low-Power 模式

| | |
|---|---|
| **决策** | 16 000 Hz，运行在芯片的 Low-Power 模式 |
| **依据 1** | 数据手册 Table 5 的采样率范围有**空档**：Low-Power 是 6.25–18.75 kHz，High-Performance 是 23–51.6 kHz。**16 kHz 只存在于 Low-Power 模式**，不是可选项 |
| **依据 2** | 高性能模式带来的收益几乎为零。Table 3（Low-Power，**标定条件就是 fS = 16 kHz**）SNR 64 dBA / EIN 30 dBA SPL；高性能模式 SNR 65 dBA / EIN 29 dBA SPL —— **只差 1 dB**。手册自己也写着 "high SNR and 120 dB SPL AOP in **all** operational modes" |
| **备选：48 kHz / High-Performance** | **没选**。理由：只多 1 dB SNR，却要付三倍数据量、一次降采样（引入自身伪影）、翻倍功耗（230→490 µA）。且 48k 不是 ASR 的原生输入 |
| **附带确认** | SCK = 64 × 16 000 = **1.024 MHz**，落在手册 400 kHz–3.3 MHz 范围内 |

## D3 · 板子只采音，不做识别

| | |
|---|---|
| **决策** | ESP32 固件只做「I²S 采集 → 打包 → 传输」，ASR 与总结全部在 PC 上 |
| **依据** | ① 经典 ESP32 算力跑不动可用的中文 ASR；② ASR 想升级模型时，改 PC 比重新烧固件快得多；③ 用户要的两个未来变更点（换传输、换 ASR）都在 PC 侧 |
| **备选：`espressif/esp-sr` 板端识别** | **没选**。识别率低、模型固定、且会把固件变成难以迭代的巨石 |

---

## D4 · 传输：串口与 WiFi 两条都做，共用帧格式

| | |
|---|---|
| **决策** | 实现 `AudioSource` 抽象，下挂 `SerialSource` 和 `TcpSource`，**二者共用同一套帧格式** |
| **依据** | 用户明确要求「两条都实现」。共用帧格式让传输层可互换，是 `AudioSource` 抽象成立的前提 |
| **实现顺序** | 串口优先（阶段 2），WiFi 后置（阶段 5）—— 串口链路已在 hello_world 阶段验证过，零新增风险 |

### D4.1 · 波特率 921600

| | |
|---|---|
| **决策** | 串口从 115200 提到 **921600** 8N1 |
| **依据** | 净荷 32 000 B/s，加 1.4% 帧头 = **32 938 B/s**。921600 8N1 净速率 92 160 B/s，占用率 **35.7%**，有 2.8 倍余量 |
| **为什么不能用 115200** | 115200 净速率 11 520 B/s，**装不下** 33 KB/s —— 差 2.9 倍，会持续丢帧 |
| **退路** | 921600 不稳就退 460800（仍有 1.4 倍余量） |

## D7 · ASR：本地优先，但留云接口

| | |
|---|---|
| **决策** | 实现 `AsrProvider` 抽象，先做本地 `FunASRProvider`，云实现留空 |
| **依据** | 用户选择「先本地跑通，留好云 API 接口」 |
| **直接收益** | **用户不需要申请任何 API key** —— 不注册、不实名、不充值、音频不出本机 |

### D7.1 · 本地引擎：FunASR **离线全链路**（2026-09-27 重定，原为流式）

| | |
|---|---|
| **决策** | `paraformer-zh` + `fsmn-vad` + `ct-punc` 三件套，整段转写 |
| **⚠️ 原决策** | ~~`paraformer-zh-streaming`~~ —— **原依据已完全失效**。原决策的第一条依据是"需求 #2 明确要求流式输出"；需求 #2 在 v1.1 被用户取消了，**理由消失，决策必须重定，不能沿用** |
| **依据 1** | 不流式后，可以挂 **`ct-punc` 恢复标点** —— 这是流式模型做不到的。**标点对 LLM 总结的质量影响很大**，这是本次变更最大的实际收益 |
| **依据 2** | 非流式模型看完整句，准确率**高于**只前瞻 300 ms 的流式模型 |
| **依据 3** | 中文原生优化（阿里达摩院），16 kHz 单声道正是其原生输入，与 D2 吻合；技术栈与 v1.0 一致，用户已装的环境不用重来 |
| **备选：faster-whisper large-v3** | **没选但保留**。中英混说更强、自带标点，但纯中文未必更强，且慢得多（large-v3 约 10~20× 实时）。既然延迟不再是约束，它比 v1.0 时期**更有竞争力**了 —— 实测中文夹英文效果差时可换 |
| **切换成本** | 两者都在 `AsrProvider` 后面，且 v1.1 的接口（`transcribe(wav_path) -> str`）比流式接口简单得多，换实现更容易 |

## D9 · 按键：延后到阶段 6，先用串口命令

| | |
|---|---|
| **决策** | 阶段 2–5 用串口命令 `start` / `stop` 触发；物理按键在阶段 6 接入 |
| **依据** | 用户选择「先不管按键，串口命令代替」。按键是**交互层**，与音频链路正交 —— 先把它排除，能把阶段 1 的风险暴露得更干净 |

### D9.1 · 按键行为：按一下开始 / 再按结束 + 静音兜底

| | |
|---|---|
| **决策** | Toggle 模式，外加「静音 5 秒自动结束」兜底 |
| **依据** | 用户确认。Toggle 适合长场景（会议记录），不会像 PTT 那样手一松就断；静音兜底防止"忘了按停" |
| **代价** | 中间停顿超过 5 秒会被提前切断 → 所以阈值必须现场标定（风险 R9） |
| ⚠️ **2026-10-04** | **"静音 5 秒"这个具体值待 D13 重新标定**（判停挪到板端 VAD 后才有条件调快）。**Toggle 模式本身不变** |

## D10 · GPIO 分配：22 / 25 / 26

| | |
|---|---|
| **决策** | WS→GPIO25，SCK→GPIO26，SD→GPIO22 |
| **依据** | 必须避开三类脚：**GPIO 6–11**（SPI Flash，碰了必死机）、**GPIO 0/2/12/15**（strapping，上电电平决定启动模式）、**GPIO 1/3**（UART0 console，占了就看不到日志） |
| **备注** | GPIO 25/26 兼作 DAC，但本项目不用 DAC，可安全用作 I²S |
| **按键（阶段 6）** | 推荐 GPIO 27（空闲、无复用冲突、非 strapping） |

## D12 · 取消流式转写，改为整体转写（2026-09-27）

| | |
|---|---|
| **决策** | 录音期间只显示状态 + 计时 + 电平条，**不做转写、不显示文字**；停止后对整段录音一次性转写 |
| **依据 1** | 用户判断：「流式转写没有特别大的用处，唤醒之后显示聆听中即可，停止后整体进行转写」 |
| **依据 2** | **这是净收益，不只是简化。** 取消流式后解锁了标点恢复（`ct-punc`），而标点对 LLM 总结质量影响很大 —— 这是"省事"之外的实质提升 |
| **依据 3** | 流式模型只前瞻 300 ms，准确率低于看完整句的离线模型 |
| **连带影响** | ① NFR-1 延迟预算整个作废重写；② **链路延迟不再重要**（PC 边收边写 WAV，早到晚到无所谓，只要不丢）→ 阶段 2 的取舍从"低延迟"变成"不丢帧"，后者容易得多；③ `FINALIZING` 状态与 `is_final` flush 消失；④ 后台总结线程消失；⑤ `AsrProvider` 接口从 `feed`/`finalize` 简化为 `transcribe(wav_path)`，**没有跨调用状态**，少了一整类 bug |
| **确认过的边界** | 「唤醒」仍指按键/命令，**不是**语音唤醒词（那会推翻"不做唤醒词"这个非目标）<br>⚠️ **该依据已于 2026-10-04 失效 —— 见下方 D12.2 说明** |
| **录音期间的电平条** | 保留，且是**有价值的**：这块模块灵敏度偏低，嘴远了拾不到（见 hardware.md §7）。电平条让你当场就知道没录到，而不用等转写完 |

> ⚠️ **这个变更的性质值得记录**：D12 不是改了个参数，而是**让 D7.1 的理由失效**。
> 原 D7.1 选 FunASR 的第一条依据就是"需求要求流式"。需求变了，**依据就没了，
> 决策必须重新论证而不是默认沿用** —— 否则会留下一个"结果正确但理由错误"的决策，
> 下次有人质疑时无法自洽。所以 D7.1 被重写了，而不是被悄悄留着。

## D12.2 · ⚠️ 依据已失效，待重审（2026-10-04）

| | |
|---|---|
| **原决策** | 「唤醒」仍指按键/命令，**不是**语音唤醒词 |
| **原依据** | ① 唤醒词会推翻"不做唤醒词"这个非目标；② **能力依据**：经典 ESP32 上只有 `wn5_hilexin` / `wn5_nihaoxiaozhi` 两个官方唤醒词，想要别的必须**付费定制**（2 万条语料、2~3 周），且官方明确"新算法不再支持 ESP32"—— 是条**技术死路**（`wakeword-research.md` §2.1） |
| **⚠️ 现况** | **依据 ② 已不成立** —— 换 S3 后 **WakeNet9 可用**，免费唤醒词更多 |
| **待重审** | ❓ **要不要做唤醒词**。这是**范围决定**而非能力决定：当初"做不到所以不做"的成分消失后，"做不做"必须重新论证，**不能默认沿用** |
| **不自动推翻的理由** | 按键有它自己的优势 —— **确定性**（不会误唤醒、不依赖唤醒词质量、无 always-on 的隐私负担）。**换板 ≠ 换交互方式** |

> ⚠️ **这又是"结论可能仍对，但理由已不成立"的一例**，与 D7.1 同型。
> 与 D7.1 不同的是：**这次我不替用户决定** —— 原决策保留，只标注依据失效、待重审。

## D13 · 「聆听结束」判定前移到板端 AFE VAD（2026-10-04）

| | |
|---|---|
| **决策** | 判停从 **PC 侧 RMS 静音检测** 前移到 **板端 AFE VAD**。**VAD 状态机形态不变**（SPEECH→录、SILENCE→停），换的是实现所在的那一端 |
| **依据 1** | 用户指示：「**完全参考 xiaozhiAI 就行，他的反应挺快的**」。xiaozhi 的判停正是板端 AFE VAD，由 `vad_state_change_callback_` 驱动应用层（`wakeword-research.md` §1.3） |
| **依据 2** | **现状是整条链路上最大的一段纯浪费**：PC 侧 RMS 要求"静音**持续 5 秒**"才发 STOP（FR-5），用户说完要干等 5 秒。xiaozhi 的 VAD 按 **32 ms 帧**实时判断 |
| **依据 3** | **结构上更合理**：现在 PC 必须**先收到音频**才能判静音 —— **判停质量与链路质量耦合**。前移后判停不依赖 PC 在线，也不受串口延迟/丢帧影响 |
| **前置条件** | **必须是 S3**。AFE/VAD 在经典 ESP32 上不存在 → **PICO 上继续走 PC 侧 RMS**。这正是 `board.h` 能力标志 `BOARD_HAS_ESPSR` 的用途 |
| **明确不做 ①** | ❌ **不引入流式 ASR**。xiaozhi 的"快"另一半来自云端流式识别，那条**会丢掉标点**（与 D12 直接冲突）。**只抄判停，不抄识别** |
| **明确不做 ②** | ❌ **不改传输方式**（仍实时流）。用户诉求是"快"，而**整段传反而更慢** —— 录 60s 之后还要再花 ~21s 传输，实时流则是边录边传、停止即可转写 |
| **已确认 ①** | **判停后由固件自己停**（`session_stop()`），随后发一个状态帧通知 PC。<br>**不采用**"只上报 VAD 事件、由 PC 决定停不停"—— 那样一来判停虽在板端，**决定权仍在链路另一端**，往返延迟会吃掉"快"的一部分收益（2026-10-04 用户「按推荐来」确认）<br>⚠️ **这是协议改动**：固件第一次**自己发起 STOP**，PC 侧要认这个新来源 |
| **已确认 ②** | **发给 PC 的仍是原始音频，AFE 只在旁边读一份做判停** —— **音频路径不变**。<br>理由：转写用的 FunASR **自带 VAD 与降噪**，喂 AFE 处理过的音频反而可能引入它不认识的失真；而 AFE 的价值在这里只是"判断有没有人在说"，不需要它的输出音频 |
| **已确认 ③** | 静音时长**初值参考 xiaozhi 的 `VAD_MODE_3`**，先把链路跑起来，再实测标定（见 §12-Q9） |
| **待办** | ① **静音阈值与静音时长必须在 S3 上实测标定**；② **静音时长是否仍是 5 秒待定** —— 太短会在换气处切断，太长则失去"快"的意义；③ FR-5 与本节的关系待同步 |
| **实现** | `afe.h` 能力抽象 + 双实现（`afe_passthrough.c` / `afe_espsr.c`），按 `BOARD_HAS_ESPSR` 编译期选择 |

> **为什么值得单列一条决策**：这不是"换个库"，而是**把状态机的一端搬家**。
> `prd.md` §2.2 的固件状态机目前是 `IDLE ⇄ RECORDING` 由 **PC 命令**驱动；
> D13 之后固件要能**自己发起 STOP** —— 固件侧第一次有了"语义判断"能力
> （哪怕只有 VAD 这一种）。
>
> **这触及 `prd.md` §1.3 的边界**：「板子只采音、不做识别」是该非目标第一次被
> 实质性放宽。**放宽的是"前端信号处理"，不是"内容识别"** —— 板端仍然
> **不跑 ASR、不理解说了什么**，只判断"有没有人在说"。**这个区分要守住**
> （理由见下方总表中的 D3 注记）。

## D14 · PICO 移出验证范围（2026-10-04）

| | |
|---|---|
| **决策** | **不再对 ESP32-PICO-V3-02 做实测验证。** S3-CAM 成为唯一的验证目标 |
| **依据** | 用户决定：「现在不用验证PICO了」 |
| **范围（重要）** | ⚠️ **只是"不验证"，不是"删代码"。** `board.h` 的 PICO 分支、`afe_passthrough.c`、`sdkconfig.defaults.esp32`、`Kconfig.projbuild` 的板子选择**全部保留** |
| **代价（明说）** | **PICO 路径从此是"未验证"状态，不是"已验证通过"状态。** 它会随代码演进**静默腐化** —— 任何只编译不实测的改动，都可能已经把它弄坏了而无人知道 |
| **为什么保留而不是删除** | ① **双板抽象本身就是有价值的架构**（`board.h` + Kconfig + 编译期选实现），去掉 PICO 分支并不能简化它；② PICO 仍是一块可用的备用板；③ **删除不可逆，保留可逆** |
| **复核时机** | 若将来确认永不使用 PICO，再考虑删除分支。届时 `board.h` 退化为单板，但抽象层可保留 |
| **对文档的要求** | PICO 的历史验收记录（阶段 1 / 阶段 2）**要标注为历史**，不能让后来人误以为"PICO 现在还是好的" |

> ⚠️ **销账 ≠ 补账。** 原本"欠 PICO 一次阶段 2 回归"这笔账，现在**是销掉了，不是补上了** ——
> 两者性质完全不同：前者意味着"我们不知道 PICO 现在还能不能用"。
>
> **推论**：从今往后，**任何"PICO 上应该没问题"的说法都没有依据**（连"改动是机械的、风险低"这种理由也不再成立，因为没人会去验证）。

## 决策总表

| ID | 决策 | 一句话依据 |
|---|---|---|
| D1 | 是 STT 不是 TTS | 四条需求全指向语音转文字 |
| D2 | 16 kHz / Low-Power | 16k 只在低功耗模式；高性能只多 1 dB SNR |
| D3 | 板子只采音（**不做内容识别**） | ESP32 跑不动 ASR，且升级模型要重烧固件。**D13 后边界收窄为"不跑 ASR、不理解说了什么"—— 前端信号处理（VAD）不在此列** |
| D4 | 串口 + WiFi 都做 | 用户要求；共用帧格式使其可互换 |
| D4.1 | 921600 | 115200 装不下 33 KB/s |
| D5 | 终端显示 | 用户选择；最易调试 |
| D6 | 不做播报 | 用户明确不要 |
| D7 | 本地优先 + 留云接口 | 用户选择；**且因此无需任何 API key** |
| D7.1 | **FunASR 离线全链路**（2026-09-27 重定） | 不流式后可挂 `ct-punc` 恢复标点，且离线模型准确率更高 |
| D8 | ollama **转写后总结一次**（2026-09-27 重定） | 滚动总结依赖流式文本，流式取消后它没有输入 |
| D9 | 按键延后 | 交互层与音频链路正交 |
| D9.1 | Toggle + 静音兜底 | 适合长场景，防忘停 |
| D10 | GPIO 22/25/26 | 避开 Flash / strapping / UART |
| D11 | docs 在 hello_world 下 | 用户指定 |
| **D12** | **取消流式转写，改整体转写**（2026-09-27） | 用户判断流式无用；且它解锁了标点恢复，是净收益 |
| D12.1 | 录音期间显示状态+计时+电平条 | 电平条能当场发现"没录到"，不必等转写完 |
| D12.2 | 「唤醒」仍是按键/命令，非唤醒词 | ⚠️ **依据已失效，待重审** —— 换 S3 后 WakeNet9 可用，`wakeword-research.md` §2.1 的"技术死路"论证不再成立 |
| **D13** | **判停前移到板端 AFE VAD**（2026-10-04） | 用户要求参考 xiaozhi（"反应挺快的"）；现状"静音 5 秒"是链路上最大的一段纯浪费。**仅 S3 可用** |
| D13.1 | 不引入流式 ASR | 会丢掉标点，与 D12 直接冲突 —— **只抄判停，不抄识别** |
| D13.2 | 传输方式不变（仍实时流） | 整段传反而更慢：录完还要再传一遍；实时流则停止即可转写 |
| D13.3 | **固件自主判停**：自己发 STOP + 状态帧通知 PC | 若改由 PC 决定停不停，"快"的收益会被链路往返吃掉 |
| D13.4 | AFE 只旁观，**发给 PC 的仍是原始音频** | FunASR 自带 VAD/降噪，喂处理过的音频反而可能引入它不认识的失真 |
| **D14** | **PICO 移出验证范围**（2026-10-04） | 用户决定。⚠️ 只是不验证、**不删代码** —— 代价是 PICO 路径会静默腐化 |
