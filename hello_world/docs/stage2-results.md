## 3. 验收过程中发现并修掉的两个 bug

**两个都是 PC 侧的，固件两次都完全正常。** 这很值得记一笔 —— 当时的直觉是
"嵌入式那侧容易出问题"，实际相反。

### Bug 1：`read_audio` 丢弃同一 chunk 内的其余帧（丢 70% 音频）

| | 修复前 | 修复后 |
|---|---|---|
| 帧数 | 1145 | **3753** |
| 丢帧 | 2596 | **0** |
| 收到时长 | 18.3 s | **59.8 s** |

**根因**：一次 `ser.read(4096)` 通常含 7~8 帧，但原实现解析出全部帧后
**只 `return` 第一帧**，其余解析出来就扔了。

**关键线索**：固件报 `deficit=9`、`tx_block_ms=0` —— 说明它 961,289 个样本里
只差 9 个、且从未阻塞。**PC 却只收到 30%**，而且 `bad_crc=0`（帧本身都是好的）。
"固件说发了、PC 说没收到、且没有损坏"这个组合，直接指向"收到了但在 PC 侧被扔掉"。

**修复**：加 `_pending` 队列暂存解析出的帧，逐个交付。

> ⚠️ 这个 bug **只有真实数据能暴露** —— 单测里的每个 chunk 只含一帧，
> 全部通过。这正是端到端验收不能省的实证。

### Bug 2：假的丢帧计数（`lost=2` 但 `bad_crc=0`）

**症状**：60 秒验收报 `lost=2`，看起来像链路丢了 2 帧。

**但这个组合自相矛盾**：真丢字节的话，解析器必然拼出半帧、CRC 校验失败，
所以 `bad_crc` 应该 > 0。`bad_crc=0` 说明**字节没丢**。

**根因**：主循环结束时 `_pending` 里还剩几帧没交付，而 `drain()` 收到的是
序号已经越过它们的帧 —— `_track` 一看序号跳了就报丢帧。
**那几帧一直躺在 `_pending` 里，并没有丢。**

**修复**：`drain()` 先把 `_pending` 交付并计入统计，再读新数据。

> 这个 bug 的性质不同：**数据没问题，是我的度量写错了。**
> 如果不追根因、只是看到 `lost=2` 就去"优化链路"，会白费很多功夫。

## 4. 本阶段确立的两个关键认知

### 4.1 `deficit` 比 `seq` 更本质

- `seq` 由**固件自己生成**：序号连续只说明"固件发出的帧都到了"，
  **完全不能说明 I²S 没漏采样本** —— 漏采的样本根本不会变成帧。
- `deficit` = 按时间应该产出多少 − 实际发出多少，这才反映采集侧。

验收必须同时看这两个，缺一不可。

### 4.2 背压（本阶段标记的主要风险）**没有发生**

原担心：`uart_write_bytes` 阻塞 → I²S DMA 溢出 → 静默丢音频。

实测：`tx_block_ms=0`（三次验收都是 0）。链路余量充足
（音频 32.9 KB/s vs 921600 波特率净速率 ~92 KB/s，占用 36%）。

**但检测机制保留** —— TX 缓冲 8192 字节 + 阻塞时长统计 + deficit 上报，
这套东西的价值在于**万一将来（比如换成 WiFi、或 PC 端卡顿）出现背压时，
它是可见的，而不是静默丢数据**。

## 6. 已知限制（不隐藏）

1. **偶发丢帧，来自 WSL USB 透传环境** —— 详见 §7。每 10 分钟约 0.5 秒音频，
   对 ASR 无实质影响。
2. **PC 停止录音时的边界效应**：WAV 比固件实际录制的少约 0.2~0.3 秒。
   原因是 PC 的计时窗口与固件的起止点不重合，属正常，不是丢数据。
   若要精确对齐，需要在 STOP 之后再喂一段尾帧给 recorder。
3. **WiFi 路径未实现**（阶段 5）。`AudioSource` 抽象已就位，加
   `TcpSource` 即可，不改下游。

## 7. 长时验收与验收标准修订（2026-09-29）

### 7.1 起因：60 秒不够，10 分钟暴露了问题

计划里就标注过「60 秒可能不足以暴露背压问题，必要时加到 5 分钟」。实测证实：

| 时长 | `lost` | `bad_crc` | 结果 |
|---|---|---|---|
| 60 秒 | 0 | 0 | ✅ 通过 |
| **600 秒（第 1 次）** | **44** | **31** | ❌ |
| **600 秒（第 2 次）** | **31** | **30** | ❌ |
| 300 秒 | 0 | 0 | ✅ |

### 7.2 排查：把嫌疑人逐个排除

**① 固件侧？→ 排除。**
`deficit=9`（96 万样本里差 9 个）、`tx_block_ms=0`（UART 环形缓冲从未填满）。

**② `uart_write_bytes` 会不会少写？→ 排除。**
我怀疑过它的返回值没被检查。读 IDF 源码确认：TX 环形缓冲存在时走
`while (size > 0)` 循环 + `xRingbufferSend(..., portMAX_DELAY)`，
**保证写完所有字节，不会提前返回**。

**③ PC 排空太慢？→ 排除，而且是我自己加的监控项证伪的。**
我先算出一个"零余量"结论：`read(4096)` 在 50ms 超时下每次固定阻塞、
只拿到 3.08 帧 → 吞吐 61.6 帧/秒，恰好等于到达速率 → 100% 利用率。
据此改成"读走当前可用的全部"，并加了 `max_in_waiting` 监控。
**结果：`max_in_waiting=511`（不到一帧）—— PC 排空得干干净净，假设被证伪。**

> 这一步的价值在于：**加监控项让假设可以被证伪**，而不是停在"听起来有理"上。

**④ 剩下的只有 USB 透传链路。**
ESP32 UART → CP2102N → USB → Windows → usbipd → WSL vhci

### 7.3 病因：一次约 500ms 的 USB 停顿

数据拟合得很干净：

| | 实测 | 按机制推算 |
|---|---|---|
| 单次丢失量 | 31~44 帧 = 504~715 ms 音频 | 一次 500ms 停顿 → 29 帧 ✓ |
| `bad_crc` ≈ 丢帧数 | 30 vs 31 | 中途中字节，每次事件丢约 1 帧 ✓ |
| CP2102N 容错窗口 | — | **仅 15.8 ms**（512 B ÷ 32.4 KB/s） |

**CP2102N 只有 512 字节缓冲 = 15.8 毫秒容错。** 查询资料确认：

- **CP2102N 手册**：>1 MBaud 必须启用硬件流控才能避免溢出；我们在 921600，
  刚好在门槛之下，但缓冲很薄。硬件流控需要 CTS/RTS —— **这两个脚在本板
  被自动复位电路占用**，用不了。
- **usbipd Issue #469**：USB/IP 引入约 0.1 秒延迟，维护者承认"会破坏任何有
  时序约束的场景"。
- **usbipd Issue #538**：CP210x 类设备在 CPU/IO 负载下更容易断。

**5 分钟那次零丢帧是关键证据**：同一份代码，10 分钟丢 31 帧、5 分钟丢 0 帧。
**如果这是代码缺陷，丢失应与时长成正比，而不是 0。**
→ 这是**环境的偶发故障，不是软件缺陷**。

### 7.4 为什么不修

| 方案 | 否决理由 |
|---|---|
| 提高 `usbipd.exe` 优先级 | 它是 Windows **服务**，改优先级需管理员权限，且**服务重启即复位**，不持久 |
| 改成 Windows 侧读串口再转发 | 需 `usbipd unbind` 把设备交还 Windows，则**每次烧录都要重新 attach**，工作流会烂掉 |
| 应用层 NACK + 重传 | 唯一真正的解法，但要改固件（PSRAM 存历史帧）+ 协议 + 记录器回填，工作量明显大于收益 |

**采纳：接受，记为环境限制。** 依据是 §7.3 的结论 —— 问题不在代码。

### 7.5 修订后的验收标准

```
① 丢失率 < 1%            （原为「丢帧 = 0」）
② I²S 无丢样本（deficit ≈ 0）
③ 样本数符合时长（±1%）
④ CRC 错误不高于丢帧数    （原为「无 CRC 错误」—— CRC 错误与丢帧同源）
⑤ TX 阻塞 < 64ms
⑥ 串口缓冲无积压 < 8KB
```

**第 ④ 条从"必须为 0"改为"不显著高于丢帧数"**，理由同上：CRC 错误与丢帧
是同一病因的两种表现，分别要求为 0 没有意义。但若 CRC 错误**显著高于**
丢帧数，说明另有问题（例如协议漂移），那时它仍会报警。

### 7.6 对将来的意义

**这是开发环境的产物，不是产品的属性。** 换到原生 Linux、或设备直连
Linux 主机，这个问题大概率不存在。**若哪天这段音频要用于更敏感的场合，
正确的解法是 §7.4 里的重传机制，而不是继续和环境搏斗。**

## 8. S3-CAM 上的验收（2026-10-04）

**结论**：✅ **通过**。而且这一轮跑在 **AFE（板端 VAD）已打开**的状态下 ——
所以它同时证明了两件事：S3 的链路可用，**且板端 VAD 没有破坏音频通路**。

### 8.1 与 PICO 的逐项对照

| 判据 | PICO（2026-09-28） | **S3（2026-10-04）** |
|---|---|---|
| 帧数（60 秒） | 3753 | **3753** ← 完全一致 |
| `deficit` | 9 | **6** |
| `lost` / `bad_crc` | 0 / 0 | **0 / 0** |
| `tx_block_ms` | 0 | **0** |
| 丢失率 | 0.000% | **0.000%** |

**两块板行为一致。** 而 S3 这一轮额外背着一个 AFE 的实时处理负载，
`deficit` 反而更小 —— **AFE 的开销在这个量级上可忽略**。

### 8.2 ⚠️ 验收脚本因 D13 改过一次

前两次跑出现"失败"，但**原因是判据过时，不是链路问题**：

```
固件状态: STOPPED by=VAD dur_ms=41536 samples=664576 ...
❌ 样本数符合时长（±1%）    664576/960000
```

- **`by=VAD`** —— 固件（S3 的板端 VAD）**自己判停了**，录了 41.5 秒就结束
- 而脚本拿"计划的 60 秒"当基准 → 判失败

**这是 D13.3 生效的证据，不是 bug。** 已修两处：

1. **脚本认得固件自停** —— 收到 `STOPPED` 就收工，不再傻等
2. **基准改用固件自报的 `dur_ms`**，而不是脚本计划的秒数

> ⚠️ **这条通用**：D13 之后"录满 N 秒"**不再是必然**。
> 任何依赖"录音时长 = 我要求的时长"的 PC 侧逻辑都要跟着改。
> 这正是当初改 D13 时预警过的缺口（"PC 侧认不出固件自己停的"），现在实际发生了。

### 8.3 顺带修掉：PC 侧端口写死

`sources/serial_src.py` 原本硬编码 `/dev/ttyUSB0`（PICO 的 CP2102N）。
双板改造当初**只做了固件侧**，PC 侧没跟上。已改为**自动挑口**：

| 板 | 设备节点 |
|---|---|
| S3-CAM | `/dev/ttyACM*`（原生 USB，**优先**） |
| PICO-V3-02 | `/dev/ttyUSB*`（CP2102N） |

⚠️ **挑完会把实际用的口打出来** —— 双板环境下不能让"这次用的是哪块板"成为隐藏状态。
也支持显式指定：`python stage2_accept.py 60 /dev/ttyUSB0`

### 8.4 一个值得记住的观察

前两次都在 **41.5s / 44.8s** 被 VAD 判停，第三次（环境安静）**录满 60 秒**。
→ 说明那两次是**环境里的真实声音**，不是系统性误报。

**这反过来验证了 VAD 的行为是对的**：有声音才判停，没声音不停。
