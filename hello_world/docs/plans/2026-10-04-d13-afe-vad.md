# D13 · 板端 VAD 判停（AFE 接入）实现计划

**日期**：2026-10-04
**上游决策**：`decisions.md` D13 / D13.1–D13.4
**现状**：`afe.h` 抽象层与 `session.c` 接线**已完成**（commit `8019e24`），
`afe_espsr.c` 是**临时骨架**（不上报事件，S3 行为同 PICO）。

---

## 0. 这份计划解决什么

把 `afe_espsr.c` 从骨架换成**真实现**，让 S3 能自己判断"说完了"，从而：

> 把"用户说完话 → 系统知道"的延迟，从**静音 5 秒**（PC 侧 RMS）降到**亚秒级**。

这是用户「**完全参考 xiaozhiAI 就行，他的反应挺快的**」这句话的直接落点。

## 1. 调研结论（决定性事实）

来源：ESP-SR **2.5.5** 源码 + 官方文档 + 二进制字符串 + issue。
证据分级见调研原文（`[源码]`/`[文档]`/`[二进制]`/`[推测]`）。

### 1.1 ⚠️ 我原先猜错的（先认错）

| 我当时的说法 | 真相 |
|---|---|
| `input_channel_num` 字段 | **整个 esp-sr 仓库 grep 不到这个符号**。通道数由 `afe_config_init()` 的**第一个字符串参数** `input_format` 决定 |

> **没有造成损害**：这个字段名**从没写进任何代码**（`afe_espsr.c` 里只写了概念"单麦克风怎么喂"）。
> 教训仍然是那条：**API 细节必须查证，不能凭印象**。

### 1.2 关键 API 事实

| 项 | 事实 |
|---|---|
| 安装 | `espressif/esp-sr` **2.5.5**，托管组件。模型（81MB）**随组件下载**，不需要额外脚本 |
| 初始化 | `afe_config_init(input_format, models, AFE_TYPE_SR, AFE_MODE_LOW_COST)` ← **v2 API**，v1 的 `AFE_CONFIG_DEFAULT` 宏已删除 |
| VAD 状态 | **轮询字段** `res->vad_state`（`VAD_SPEECH=1` / `VAD_SILENCE=0`），**没有回调** |
| **内置判停** | ✅ **`vad_min_noise_ms`（默认 1000）就是"说完话"的判定** —— 连续静音这么久才翻回 SILENCE。**不需要自己数帧** |
| 起始判定 | `vad_min_speech_ms`（默认 128）—— 语音要持续这么久才算"开始说" |
| 帧长 | **必须运行时查** `get_feed_chunksize()`，**不能写死**。32 ms = 512 样本 @16k |
| **feed/fetch 比例** | ⚠️ **不保证 1:1**（issue #27 实测过 feed 256 / fetch 512）。`feed()` **签名里没有长度参数** |
| 单麦克风 | `input_format = "M"` —— v1 文档**明文支持**（"if AEC is not required… users can only configure one channel of mic data, and the ref_num can be set to 0"），v2 二进制证据一致。**但官方 v2 没有任何例子用 `"M"`** |
| 内存 | 整条流水线（MR+SR+NS+VadNet+WakeNet）S3 实测：**60.1 KB internal + 739.7 KB PSRAM**。我们关掉大半，会更少（**但"仅 VAD"的官方数字查不到**） |

### 1.3 已知的坑（都是真 issue）

| # | 坑 | 对我们的影响 |
|---|---|---|
| **#143** | **`models` 传 `NULL` → VadNet 静默不加载，退回 WebRTC VAD**（敲桌子被判成 SPEECH） | ⚠️ **最关键** —— 决定了要不要改分区表，见 §3 |
| **#168** | `vad_cache` 处理不当 → **丢第一个字** | ✅ **我们不受影响**，理由见 §2.3 |
| #232 | 2.4.7 的 `reset_vad()` 堆越界 | 避开即可，我们用 2.5.5 |
| #157 | feed/fetch 速率失衡 → `Ringbuffer full` 刷屏 + 结果全错 | 需盯 `afe_ringbuf_size` 与喂取节奏 |
| — | `W: Noise Suppression may reduce the accuracy of speech recognition` | **NS 关掉** |

## 2. 架构设计

### 2.1 ⚠️ 任务模型 —— 本次最大的架构变化

**`fetch()` 默认阻塞 2000 ms。绝不能放进主循环** —— 放进去就是 2 秒的音频黑洞。

我们的主循环节奏是 **16 ms 一块**，而 AFE 是**异步**的、内部有自己的任务。

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）主循环非阻塞** | `feed()` 本身是写环形缓冲（非阻塞）；取结果用 `fetch_with_delay(afe, 0)`，无数据返回 `NULL` | **不增加任务**，与现有"单主循环"架构一致 |
| B 独立 feed/fetch 任务 | 照官方例子开两个任务 + 队列通信 | 更贴官方，但要引入任务间同步与 PCM 复制 |

**选 A**，理由：我们的负载远低于官方例子（它们要同时跑唤醒+识别），
而 A 不改变现有架构。**若实测发现 `fetch_with_delay(…, 0)` 不可用或丢结果，再退回 B** ——
届时 `afe.h` 接口**不用改**（只是把队列操作放进现有函数体）。

> **接口不用改**：`afe_feed()` / `afe_poll_event()` 的语义（喂进去、非阻塞取事件）
> 对 A 和 B 都成立。这正是抽象层的价值。

### 2.2 喂取节奏

```
session_tick()  每 16 ms：afe_feed(pcm, 256)
                          ↓  内部攒帧
afe_feed()      攒够 512 才真调 feed()   → 每 32 ms 喂一次
afe_poll_event() 每次主循环非阻塞取一次   → 有结果就读 vad_state
                          ↓
SPEECH → SILENCE 跳变 = SPEECH_END → session_stop_by("VAD")
```

- **攒帧是必须的**：我们 256 样本/次，AFE 要 512（32 ms），且 `feed()` 没有长度参数 —— 喂短了会越界读且**不报错**
- **节奏天然匹配**：喂 2 次（32 ms）→ 取 1 次（32 ms）

### 2.3 ★ 为什么 `vad_cache` 对我们不重要

issue #168 说"不处理 `vad_cache` 会丢第一个字"，但那**是针对"用 VAD 触发开始录音"的场景** ——
VAD 有 1–3 帧固有延迟，所以它把触发前的音频通过 `vad_cache` 补给应用层。

**而我们的录音开始是按键/命令触发的**（D12.2，不是 VAD 触发），VAD **只负责判停**。
判停时那 1000 ms 静音**早就通过实时流发给 PC 了**，不存在"补发"的需求。

> ⚠️ **但这条要记住**：将来若改成"VAD 自动开始录音"，`vad_cache` 立刻变成必须处理的项。

### 2.4 内存与配置

| 项 | 取值 | 理由 |
|---|---|---|
| `afe_type` | `AFE_TYPE_SR` | 官方 issue #143 明确建议；不含非线性降噪 |
| `afe_mode` | `AFE_MODE_LOW_COST` | 我们只要 VAD，不需要 HIGH_PERF |
| `memory_alloc_mode` | `AFE_MEMORY_ALLOC_MORE_PSRAM` | S3 有 8 MB PSRAM，internal RAM 更宝贵 |
| `aec_init` | `false` | 无参考信号（不做播报） |
| `se_init` | `false` | 单麦，本来就自动关 |
| `ns_init` | `false` | 库自己警告"NS 会降低识别准确率" |
| `wakenet_init` | `false` | D12.2 待重审，**本次不引入** |
| `agc_init` | `false` | 不需要 |
| `input_format` | **`"M"`** | 单麦无参考 |

## 3. ⚠️ 决策点：要不要 VadNet（= 要不要改分区表）

这是**本计划唯一需要用户拍板的地方**。

| | 方案甲：先用 WebRTC VAD | 方案乙：直接上 VadNet |
|---|---|---|
| `models` | `NULL` | `esp_srmodel_init("model")` |
| **分区表** | ✅ **不用改**（维持 `SINGLE_APP_LARGE`） | ⚠️ **必须改成自定义 CSV**，加 `model` 分区 |
| Kconfig | 不用动 | 要选 `SR_VADN_*` |
| Flash 占用 | 0 | ~292 KB（`vadnet1_medium`） |
| 质量 | 差 —— **敲桌子会被判成 SPEECH**（issue #143 实测） | 好 |
| 风险 | 低 | 中（分区表改错会起不来） |

**推荐：分两步走，而不是二选一。**

```
Task 2–3：先用 WebRTC VAD（models=NULL）跑通整条链路
          → 验收点：vad 命令能看到 SPEECH/SILENCE 跳变
Task 4：  再加 model 分区 + VadNet
          → 验收点：敲桌子不再被判成 SPEECH
```

**理由**（与 PRD 风险 R6 处理 FunASR 模型的方式一致）：
- 先跑通**再提质量**，每一步都可独立验收
- 万一 `"M"` 单麦格式在 v2 上有问题（**官方无 v2 样例，这是最大的未知**），
  在 WebRTC 阶段就能暴露，**不必先趟分区表的雷**
- 若 WebRTC VAD 实测够用，直接省掉 Task 4

### Task 2：`afe_espsr.c` 真实现（WebRTC VAD 版）

```c
#include "esp_afe_sr_iface.h"
#include "esp_afe_config.h"
#include "esp_afe_sr_models.h"

static const esp_afe_sr_iface_t *s_afe;
static esp_afe_sr_data_t        *s_data;
static int  s_chunk;          /* 每通道样本数，运行时查询 */
static int  s_nch;            /* 通道数，"M" → 1 */
static int  s_fill;           /* 攒帧计数 */
static int16_t s_frame[AFE_MAX_CHUNK];
static afe_event_t s_pending;
static bool s_was_speech;

esp_err_t afe_init(void) {
    afe_config_t *cfg = afe_config_init("M", NULL, AFE_TYPE_SR, AFE_MODE_LOW_COST);
    if (!cfg) return ESP_FAIL;
    cfg->aec_init = cfg->se_init = cfg->ns_init = false;
    cfg->wakenet_init = cfg->agc_init = false;
    cfg->vad_init = true;
    cfg->vad_mode = VAD_MODE_1;
    cfg->vad_min_speech_ms = 128;
    cfg->vad_min_noise_ms  = 1000;     /* ← Q9 要标定的就是这个 */
    cfg->memory_alloc_mode = AFE_MEMORY_ALLOC_MORE_PSRAM;

    afe_config_print(cfg);             /* 官方排错第一步：打印真实生效值 */
    s_afe  = esp_afe_handle_from_config(cfg);
    s_data = s_afe->create_from_config(cfg);
    afe_config_free(cfg);
    ...
    s_chunk = s_afe->get_feed_chunksize(s_data);
    s_nch   = s_afe->get_feed_channel_num(s_data);
    ESP_LOGI(TAG, "feed chunk=%d ch=%d", s_chunk, s_nch);
    return ESP_OK;
}

void afe_feed(const int16_t *pcm, int n) {
    /* 攒够一帧再喂 —— feed() 没有长度参数，喂短了会越界读且不报错 */
    ...
    while (n > 0) { copy into s_frame; if (s_fill == s_chunk) { s_afe->feed(s_data, s_frame); s_fill = 0; } }
}

afe_event_t afe_poll_event(void) {
    /* 非阻塞取：有结果才更新 vad_state 与事件 */
    afe_fetch_result_t *res = s_afe->fetch_with_delay(s_data, 0);
    if (res && res->ret_value != ESP_FAIL) {
        const bool sp = (res->vad_state == VAD_SPEECH);
        if (sp != s_was_speech) {
            s_was_speech = sp;
            s_pending = sp ? AFE_EVENT_SPEECH_START : AFE_EVENT_SPEECH_END;
        }
    }
    afe_event_t e = s_pending; s_pending = AFE_EVENT_NONE; return e;
}
```

**验收**：S3 编译通过；上板 `cfg` 命令显示 `AFE/VAD : esp-sr`，`afe_config_print()` 里
`input_format` / `pcm_config` / `aec_init` 与预期一致。

### Task 3：上板验证 VAD 能工作 ← **第一个真实里程碑**

```bash
idf.py -p /dev/ttyACM0 flash monitor
mic> vad 20
```

**验收**：
1. 说话时出现 `SPEECH`，停下约 1 秒后出现 `★ SPEECH_END`

3. 控制台无 `Ringbuffer ... is full` 刷屏

> ⚠️ **第 2 条是本次最大的技术风险**：AFE 处理耗时若超过 16 ms，
> 主循环跟不上，I²S DMA 溢出 → **静默丢音频**。
> 好消息是我们**有 `deficit` 指标能立刻发现**（阶段 2 建立的）。

**这一步若失败**，退路依次是：① 改用独立任务（方案 B）；
② `AFE_MODE_HIGH_PERF`；③ 降 `dma_frame_num` 之外的循环开销。

## 8. 实测结果（2026-10-04，S3-CAM）

### 8.1 ✅ Task 3 的两条关键验收都过了

```
I AFE: Input PCM Config: total 1 channels(1 microphone, 0 playback)   ← "M" 被接受
I AFE: AFE Pipeline: [input] -> |VAD(WebRTC)| -> [output]             ← 只有 VAD
I afe_espsr: feed: 每通道 512 样本 × 1 通道                            ← 与攒帧设计吻合

STOPPED by=CMD dur_ms=30048 samples=480768 expected=480780 deficit=12 tx_block_ms=0 OK
  lost=0   bad_crc=0
```

| 验收项 | 结果 |
|---|---|
| **`input_format="M"` 被接受**（§5 风险表第一行，**最大未知**） | ✅ **排除** |
| **AFE 没拖垮 16ms 循环**（§5 风险表第二行） | ✅ `deficit=12`，与阶段 2 的 9 同量级 |
| AFE 日志污染音频流 | ✅ `bad_crc=0` |
| D13.3 的 `by=` 协议改动 | ✅ |

### 8.2 ⚠️ 任务模型改过一次 —— 计划的"方案 A"被硬件证伪

§2.1 原定**方案 A（主循环非阻塞轮询）**。实测：

```
W AFE: Ringbuffer of AFE is empty, Please use feed() to write data   ← 12 秒刷 21 条
```

**根因**：AFE 是 **32ms 节拍的流水线**（还带处理延迟），用 16ms 去轮询它，
每次空取都会打印警告。

**已改用方案 B（独立任务阻塞 fetch）**，也就是官方例子的用法。

> **这正是 §2.1 预留退路的原因** —— 当时写的是"若实测发现 `fetch_with_delay(…, 0)`
> 不可用或丢结果，再退回 B"。**退得对。**

**顺带修掉的噪音**：`esp_log_level_set("AFE", ESP_LOG_ERROR)`。
⚠️ **不是把警告藏起来** —— 取空次数自己统计、每 200 次汇总一条，信息没丢只是不刷屏。
且**取空在"按需录音"架构下本就是正常的**：官方例子 feed 永不停歇，我们是录了才有音频。

### 8.3 ⬜ 仍未验证的一项（**需人配合**）

**有人说话时能否检测到 `SPEECH`** —— `vad` 命令目前只观察到 `init → silence`
（因为测试时没人说话）。这是 Task 3 的第 1 条验收，也是整个 D13 的价值所在。

```bash
# 跑起来后对着麦克风说话，然后停顿
mic> vad 20
# 预期：说话时 speech，停下约 1 秒后 ★ SPEECH_END
```

### 8.4 新发现的缺口

**PC 侧 `sources/serial_src.py` 写死 `/dev/ttyUSB0`** —— 双板改造只做了固件侧。
S3 是 `/dev/ttyACM0`，跑 `stage2_accept.py` 必须先改端口。**应作为独立的适配项补上。**
